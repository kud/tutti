# Design direction (Iris)

Scope: tutti is the living room's remote for the BRAVIA, the Theatre Bar and the computer shown on the TV (Erwann, 2026-10-25; « c'est pas qu'un Mac, ça peut être n'importe quel type d'ordi »: macOS, Windows or Linux). Not a general-purpose Bluetooth keyboard or trackpad (« L'idée de tutti est d'être une remote control pour TV et Mac sur TV, pas un trackpad générique. »): two kinds of Bluetooth target, the TV and the computer, and no trackpad feature beyond what controlling the computer on the TV needs.

The app replaces BRAVIA Connect day to day, with a Google TV–grade remote at its heart. Setup and room calibration stay in BRAVIA Connect.

## Principle: calm on top, deep underneath, and always say what unlocks more

Erwann, 2026-10-24: "Il faut vraiment que ce soit une app à la fois amazing UX et une app de geek dans les options. Assister aussi l'utilisateur pour lui dire ce qu'il doit faire s'il veut plus d'options, genre PSK etc."

- **The surface is calm.** The remote, the Son sheet and the scenes are for every evening: no protocol words, no ports, no readouts nobody asked for. A missing capability is never a dead control or a silent absence; it is one plain line saying why, with a way forward.
- **Depth lives one level down.** Everything an enthusiast wants (diagnostics, technical details, the readouts and hidden options the reverse map brings, `docs/reverse/bravia-connect.md`) sits in Settings › Advanced, behind developer mode. It may grow as large as it likes; it never leaks onto the everyday screens.
- **tutti always tells you what unlocks more, and how.** What tutti can do depends on setup done on the TV and in BRAVIA Connect. Each such step has one home, "What tutti can do" (below), that says whether it is done, what it unlocks, the exact menu path, and a button into tutti's own field for it. Wherever a missing step blocks something, the message that says so offers "Show me how", opening that step.

### What tutti can do (the setup checklist)

Settings' first row, "What tutti can do", reads the progress in words ("2 of 4 set up · next: IP control", or "All set up") and opens one screen (`ui/settings/UnlockScreen.kt`; the rules, pure and tested, in `Unlocks.kt` / `UnlocksTest`). A short intro ("The remote works as soon as the TV is paired…"), then one group per device:

- **TV**: *TV remote* (pairing, 6466/6467: the base), *IP control* (the code shown on the TV, or a PSK: TV settings, what's playing and on which input, the TV's own apps and icons, waking a TV that is fully off, since IP control is where tutti learns its hardware address), *Remote start* (the TV stays reachable in standby, read from `getWolMode`).
- **Soundbar**: *Soundbar* (External control in BRAVIA Connect, TCP 33336: the rail, mute, the Son sheet, the bar in scenes, one Power).
- **For the curious**: *Developer mode*. Optional, outside the count.
- **Sony account**: *Sony sign-in*, "Coming later", nothing to do. Optional, outside the count; it becomes a real step when phase 2 of the reverse map lands.

Each step is one row: a status disc, the title, the status in a word, and what it unlocks in one small line under it. The status never rests on colour (Erwann is colourblind): each has its own glyph and word, done (filled disc, tick, "Done"), not yet (empty ring, "Not yet"), set up but failing (warning triangle, "Needs a look", plus "Now: access refused (code or PSK)" in the link's own words), checking (circling arrows), waiting on an earlier step (padlock, "Pair the TV first"), unknown (question mark, "Can't tell from here": Remote start before IP control answers), coming (timer). Only "Done" also fills its disc in the primary container, as emphasis on top of the tick.

One step is open at a time, and the screen opens on the one asked for (a nudge's) or else the next to do, failing steps before undone ones. Open, it shows "How" with the exact path on the TV or in BRAVIA Connect, numbered, and one button into tutti's own field: "Show a code on the TV" (the IP control dialog in place, asking the TV at once), "Pair the TV", "Add the soundbar" (the onboarding's Bar step alone), "Turn on developer mode". Done steps keep a quiet way back ("IP control…", "Turn it off"); IP control done adds whether waking from off is ready. Menu paths are Sony's names in each language: English "Settings → Network & Internet → Local network setup → IP control", "Normal and Pre-Shared Key", "Remote start"; French "Paramètres → Réseau et Internet → Configuration du réseau local → Contrôle IP", « Normale et clé pré-partagée », « Démarrage à distance », and BRAVIA Connect's "Contrôle externe (External control)".

**IP control: the code shown on the TV first (Erwann, 2026-10-25: « ajoute le PIN Sony aussi », then « Je suis friand des PIN affichés sur l'écran »).** Everywhere IP control is offered (the TV row in Settings › Devices, the checklist step, the TV settings explainer, the onboarding's Ready step), one dialog, `IpControlDialog`: what it gives in one line, then the code as the first choice, in a filled card labelled "Recommended" in words (never colour alone), "Code shown on the TV" and one button, "Show a code on the TV"; below it a plain text button, "Use a PSK instead", which opens the PSK dialog as it was. Under both, in small text, what the TV needs: IP control on with Authentication "Normal" or "Normal and Pre-Shared Key", and the menu path marked as the one in Sony's guide. The code flow: "Asking the TV for a code…", then "Enter the code shown on the TV", a 4-digit numeric field that takes digits only, "Confirm" once four are typed, "Show another code" beside it; a wrong code keeps the field with "That code doesn't match. Check the TV screen and try again."; success says "Done: IP control is on." in words, and each failure says its cause (no answer, IP control or "Normal" off, the screen off, the TV's certificate changed). Buttons that already say "Show a code on the TV" (the checklist step, « Renouveler le code ») skip the choice and ask the TV at once. The TV row's action is « Contrôle IP »; when the TV refuses the cookie even after renewal, the row adds « Contrôle IP : code à renouveler » and the action becomes « Renouveler le code ». The checklist step is "IP control" (no longer "IP control and PSK") and its "How" leads with the code.

Nudges, where a missing step is the cause: a failed wake carries "Show me how" (no hardware address learnt → IP control; asleep or not found → Remote start; the bar silent → Soundbar), which takes the message's one action ahead of "Copy details"; the TV settings explainer adds "See everything tutti can do"; with no bar, the Son sheet and Settings already offer "Add the soundbar".

### Advanced

Settings › Advanced holds the developer-mode switch, and with it on, Diagnostics and Technical details (`TechnicalScreen`: per device, the address, each link, whether a PSK is stored and whether the hardware address is learnt, never their values, Remote start, the model and generation, the features the bar refused; tutti's version). The reverse map's phase-2 readouts and hidden options join here as rows or screens of their own. Nothing in Advanced is needed day to day, and nothing from it appears elsewhere.

### Leaving setup

Opened from an app already set up (Settings' "Run setup again", "Add a device", "Add the soundbar", the Son sheet's or a checklist button), setup has a Back at the top left (48 dp, "Leave setup" to TalkBack), and the system back does the same: any pairing in progress is dropped and you land where you came from, nothing changed. Inside the flow, back from the code still steps back to the search first. The very first launch has no such exit: there is nowhere to go back to (Erwann, 2026-10-24: "il faudrait pas un bouton annuler ou retour ici ?").

One tap from the remote: power, volume, mute, input, keyboard, any scene, any shortcut, Night, Voice.
Apps have one door: the Apps pin, or the ⋮ menu's Apps once no pin opens it (see Shortcuts); the TV's own apps screen is the first line of its sheet (Iris, 2026-10-24). All keys carries no apps and no "All apps" key: numbers and channels, colour keys, the TV keys, and Quick settings on the last row. The TV keys wear their glyph over their name (Erwann, 2026-10-25: « des icônes ici », « surtout sur la partie TV »), the one `keyIcon` gives that key everywhere (Menu is the options mark ⋮, kept apart from Guide's list), in tiles as tall as the colour keys; CH+ and CH− wear the channel arrows over "CH". Digits, Jump and TV stay words, the colour keys their swatch and name.

Two levels deep at most.

### "Son" sheet
Folded, it shows its handle and one line, "Sound" and what is on (with the bar on its own, the source first: "Sound · Bluetooth · Night"), and nothing else: the rest stays transparent and out of TalkBack until the sheet opens, then fades in by opacity (Erwann, 2026-10-24: the gesture bar's inset had let the top of "Bar input" show under the summary).

Sound field, Voice, Night, Auto volume, 360 Spatial (and Voice Zoom 3 when offered) as large toggle tiles: only real on/off settings are tiles. Each tile has its glyph top-start and its state mark top-end on one line, the name and its state under them, so the name keeps the tile's whole width (Iris, 2026-10-25). DRC and IMAX are three-way (Auto, On, Off), so each is a labelled row of three segments under the tiles, every option in view and the current one ticked and filled, read by TalkBack as the setting then each option as a radio button, as the bar settings screen lists the same choices (Erwann, 2026-10-24: "DRC est bizarre car c'est un toggle mais en fait il y a trois options"); Bass and Rear level as sliders; Voice Zoom 3 as a level slider only if the bar answers the capability probe. The rule is general (`soundSheetLayout`, tested): only a `Toggle` is a tile, every `Choice` gets all its options, a `Level` is a slider. Every documented value is listed, and a value the bar refuses (`ERR`/`NAK`) or never answers is rolled back to the confirmed one and remembered for the session (`TheatreState.refusedValues`): its segment, or its line in the bar settings menu, wears the warning glyph and the word "refused", the row says "The bar refused Auto. Tap it to try again.", and it stays tappable as a retry (Erwann, 2026-10-24: "tout lister et afficher une erreur quand l'option ne marche pas"). A greyed setting always shows its reason ("Voix désactivée : virtualiseur actif"), never hidden. "Recalibrer dans BRAVIA Connect" deep link. With no bar added, "Add the soundbar" sits under the title and opens the onboarding's Bar step alone.

"Bar input" sits above the tiles in the same dress as DRC and IMAX (Iris, 2026-10-24, after dev.75's chips wrapped AirPlay 2 onto a line of its own): its label with the current value on the right, then one outlined row of five segments, each a 20 dp icon over a `labelSmall` name (TV, HDMI 1, Spotify, Bluetooth, AirPlay). The chosen one is filled and its tick replaces its icon; Spotify wears its own mark, monochrome from Simple Icons as on the "On the bar" card (Erwann, 2026-10-25), and Bluetooth and AirPlay their symbols. A choice is optimistic like a tile (an arc past 150 ms, a refusal moves it back with reject and "Didn't take · try again" for 3 s); a refused input wears the warning glyph and the line under the row says "The bar refused …". TalkBack reads "Bar input", then each input as a radio button. With more than five inputs (the bar reporting one tutti doesn't know), the row scrolls sideways at a fixed segment width; it never wraps (`barInputScrolls`, tested).

Every section says what it does (Iris, 2026-10-24, from Erwann: "un moyen d'être explicatif sur chacune des options"): one quiet "?" (`ic_help`, 48 dp target, `onSurfaceVariant`) at the end of each section label, never an (i) per tile and never a long press, which nobody finds. The sections are Bar input, Effects (the tiles, under a label of their own), DRC, IMAX and Levels (Bass, Rear level, Voice Zoom level). The "?" opens a `TuttiSheet` titled with the section, its title pinned (`PinnedHeader`), with one or two plain sentences per setting, under each setting's name when the section holds several. The same sentence is each control's TalkBack hint, after its name and state (`explanation()` and `withHint()` in `SoundExplain.kt`, tested), so the two never drift. Strings live in `strings_explain.xml`. Accuracy is the rule: each line says only what Sony documents, and a claim that can't be confirmed is cut, not guessed (DRC's Auto says "when the source asks for it", not which formats; IMAX's Auto "leaves it to the bar"). TV settings get no "?".

### Sheets
Every sheet (Son, All keys, Apps, a pin's editor, the action picker) can rise to just below the status bar and no further: its handle and title always show, and what doesn't fit scrolls inside the sheet. Modal sheets go through `TuttiSheet` (`ui/common/Sheets.kt`).

The title (and a search, where there is one) stays put; only the body scrolls (Iris, 2026-10-24, from Erwann's dev.75 screenshots, where the Son sheet's "Sound" line and the picker's search slid half under the handle). `PinnedHeader` draws it: the Son sheet's "Sound · …" line, the action picker's title, search and filter chips, the Apps sheet's title and subtitle. Once the body has scrolled, a hairline in `outlineVariant` shows under the header, faded in by opacity (its own reduced-motion form). Folded, the Son sheet's peek is exactly its header, as before. The rule is general (Erwann, 2026-10-24: "chaque titre dans un bottom sheet devrait rester en haut et le reste scroll"): every sheet with a title pins it, Power, All keys and a pin's editor (whose Save stays in reach) included; a new sheet has a title and pins it.

Only the top moves a sheet (Erwann, 2026-10-25: « tout le contenu devrait scroller et pas que les boutons […] C'est juste principalement le haut qui devrait faire ça »; a drag between the Apps tiles slid the whole sheet when he meant to scroll). The handle and the pinned header drag it; everything below the header belongs to the body, gaps, padding and the space under a short list included: a drag there scrolls, or does nothing when there is nothing to scroll, and never moves the sheet, not even a pull-down at the top of the scroll. The scrim, back and the handle's own TalkBack actions still close a modal sheet, and the Son sheet's folded peek still opens from anywhere on it, since only downward drags are kept from the sheet. `PinnedHeader` holds the rule for every sheet; a full-height body (Apps, the action picker) fills down to the sheet's foot so the whole of it scrolls.

A key that opens a menu on the TV closes its sheet; a key pressed again and again keeps it open (Erwann, 2026-10-25: « Si je clique sur Subtitles, il faut que je recache la bottom sheet pour pouvoir contrôler les subtitles »). Subtitles, Audio track, Menu, Guide, Info, Input and Quick settings open something on the TV that is then driven with the pad, so a press sends the key and the sheet goes, leaving the remote with the pad in view; transport (previous, rewind, play/pause, fast forward, next), digits, channel up and down, Jump, Live TV and the colour keys stay, ready for the next press. One rule for every sheet that sends keys, the playback sheet and All keys alike (`keyClosesSheet`, `ui/remote/SheetKeys.kt`, tested); a new key joins `TV_MENU_KEYS` when it opens a menu on the TV. A key refused (the Mac targeted, the link down) still closes the sheet, its message saying why; only a key sent has TalkBack hear "Sent to the TV. Use the pad in its menu.", since the sheet vanished under its focus. The Power sheet's Sleep timer is not a menu key: each tap steps the TV's timer, so that sheet stays open.

### Now-showing card: playback and app actions (Erwann, 2026-10-25)

Tap (« la lecture est pas mal »): a `TuttiSheet` whose pinned header is the card itself (icon, name, detail) under a small "Playback" label. Five round keys, previous, rewind, play/pause, fast forward, next, play/pause larger in the primary container; then compact chips (see "Room in the playback sheet" below). Every one is a remote v2 media key sent through `sendTvKey` (`controller.key`), so a key pressed in a blip follows the TV link's rules: play/pause waits for the link, the rest are refused with their message (`TvLinkRule.HOLDABLE`). Only what is real: no source tells tutti whether an app is playing, its title or its position (remote v2 reports only the foreground package; `getPlayingContentInfo` answers for the tuner and inputs, not for apps), so play/pause is one toggle glyph that claims no state, and a position shows only when Cast reports one (the timeline, below). ## Gestures: the long-press grammar and the discoverability rule (Erwann, 2026-10-25)

**Grammar.** Tap does; long press opens the thing's menu (first row the most useful, last "Pin to dock" or "Edit"); drag sets a continuous value. No double tap anywhere: it would delay every OK by about 300 ms. When the menu would have a single row (an effect tile, a DRC or IMAX choice, a key in All keys, a TV setting value), the long press goes straight to that row: "Pin to dock" opens the slot dialog.

**"Pin to dock" everywhere it makes sense.** Effect tiles, bar inputs, DRC and IMAX choices, All keys, TV settings values: one `DockPinner` (`ui/remote/PinAnywhere.kt`) writes the dock's own model (`DockAction`), so the pin is like any other.

**Bar inputs.** Long press a segment: Pair a device (Bluetooth only, first), Rename (tutti only), Hide (never the input playing now), Pin to dock. Hidden inputs come back from Settings › Soundbar › Hidden inputs.

**OK held (Erwann, 2026-10-25: « le long press ne marche pas sur le centre du D-pad »).** OK is the one long press that is not tutti's menu: it is the TV's, the way a physical remote's OK held is, and apps open their own options on it (YouTube's "Go to channel"), which is the grammar's "long press opens that thing's menu" read literally. A finger still on OK (D-pad) or still on the touchpad past the long-press timeout puts the key down on the TV (remote v2 START_LONG) and the lift brings it up (END_LONG); the key stays down at least `KeyHold.MIN_HOLD_MS` (700 ms, past the TV's own timeout) so a lift right after the haptic still reads as held, and never past `MAX_HOLD_MS` (10 s). A second finger or a cancelled touch lifts it at once, so the two-finger gestures stay as they are; a tap is still a short OK (`OkHold`, tested). Where it goes follows the target (`Targeting.hold`): the TV over Bluetooth holds the keyboard report, a computer gets one plain Enter (a held one would repeat), and TalkBack's "Hold OK" action and a pin's "Hold" step hold for the minimum. Until this, START_LONG and END_LONG went out back to back, which the TV read as a plain OK.

**Back and Home (Iris, 2026-10-25, benchmark item 1).** Long-press Back goes back to the previous app (the living room's alt-tab); long-press Home opens the Apps sheet with "Recent" on top: up to four apps used before the one in front, newest first, never Google TV Home or Settings (`AppHistory.others`, tested), then "All apps". It replaces the TV's own switcher (APP_SWITCH, 187), which Google TV ignores; that key stays in All keys. Both are defaults: an action he assigns wins, and the default says itself once with "Change". The Recent row is also the visible way in (rule 4).

**Launcher.** Long press on tutti's icon: the first three scenes in his order, then Keyboard; kept in step with the scenes whenever the app is in front.

**Discoverability: a hidden gesture exists only if all five hold.**

1. It shows it is coming: the ring sweeps the control's edge from 150 ms to the long-press timeout (`holdForMenu` for controls that keep their own tap, `longPressRing` on the round keys), and the menu, dialog or tag names what it did.
2. It is listed in the registry, `ui/common/Gestures.kt`, the single source of truth, which the remote's top bar shows as the "Gestures" sheet: the "Gestures" row of the "⋮" menu, after "Scenes" and "Settings" (Erwann, 2026-10-25; `TopBarTest`). A gesture not in the registry does not ship.
3. At most one hint per gesture, once, at the right moment; never two the same day; showing is spending, so a dismissal is permanent (`GestureHints`, `TuttiController.takeHint`).
4. Never only behind a gesture: each action also has a visible way in (a menu, a sheet, Settings).
5. TalkBack first: every long press is a `CustomAccessibilityAction` named by what it does, never "long press"; state never rests on colour; 48 dp targets; a TV or bar control whose link is down refuses its long press too (a bump), except Power.

## The TV's link: calm, then honest

Iris, 2026-10-24, from Erwann's "si les touches ne marchent pas à ce moment-là, peut-être que c'est mieux". The rule is `TvLinkRule` (`controller/TvLinkRule.kt`, tested); the remote reads its result, `Links.tvShown`, and Technical details keep the raw link.

- Before: every drop of the remote v2 link showed at once (chip "BRAVIA 8 unreachable" in red, then "Connecting…", the card on "TV out of reach"), even for a one-second blip; and a key pressed meanwhile was dropped by `AtvRemote.send` with nothing said and nothing felt beyond the press's own click.
- A blip shows nothing. For 3 s after a link that was up drops, the remote stays as it was, the last app included. A reconnect is a 1 s backoff, then TLS and the configure exchange: about 1.5 to 2.5 s on a home LAN, so 3 s covers the first retry with margin.
- Past 3 s, quietly: the chip's dot becomes the open ring with "Reconnecting to the TV…" (onSurfaceVariant, never the error colour), and the card says "Reconnecting…" over "Keys work again once the TV answers", with the turning-arrow glyph, not the warning triangle.
- Past 20 s (the 1, 2, 4 and 8 s backoffs and their attempts), the stronger state comes back: "BRAVIA 8 unreachable" in the chip, "TV out of reach" on the card, the down dress on every TV control (Visual, State). A retry after that never flickers back to "Connecting…". A link never up this session (the first connect), Needs pairing and no TV show as they are, with their own messages and actions.
- A link that is down wins on the card over a channel or input that REST still reports: the card vouches for the keys. Standby still wins over everything.
- From 3 s on (reconnecting, then out of reach) every TV control wears the down dress and a tap sends nothing (Visual, State), so the rules below apply to a key pressed inside the blip, or sent from elsewhere (a widget, a scene).
- A TV key pressed while the link isn't up never vanishes. One-shot keys whose effect doesn't depend on focus (Home, Back, play/pause, play, pause, stop, Guide, Settings, All apps, TV) wait up to 2 s and go the moment the link is back, newest wins: a soft bump and "Sending when the TV is back…". Everything else is dropped with the reject haptic and "Not sent: waiting for the TV": D-pad and OK (a burst of arrows landing late, or OK on whatever took focus), digits and channel steps, colour keys, skips, long presses, and power, which has its own wake path. A held key that doesn't make it says "Not sent: the TV didn't come back in time". Past give-up it is "Not sent: the TV is out of reach", and with pairing lost "Not sent: pair the TV again". The same words don't repeat while they still show, so a burst of arrows is one message and a reject per press.
- The bar's keys (volume, mute) are their own link and never wait on the TV's.
- **Implicit wake (Erwann, 2026-10-25, delegated: « Fais tout ce que bon te semble »; Maya).** Home and Play/Pause pressed while the TV is *known* asleep (it reported standby; not merely out of reach) wake it, then go once, as any physical remote wakes the screen. This reverses the standby rule "sends nothing" for those two keys only, because they mean "I want the TV": Home is where the TV starts, and Play/Pause on a sleeping TV can only mean "carry on". Every other key keeps the standby refusal; a TV out of reach is a fault, not standby, so nothing wakes it blind; a long press never wakes. The wake is Power's own path (`power(TV, on)`: the remote's power key, REST, Wake-on-LAN), the key goes once the TV says it is on, within the wake's 12 s plus 2 s for its power report, newest key wins, and "Waking the TV…" shows meanwhile. A failed wake says so as Power's does. Rule: `TvLinkRule.wakesTv` (tested); the bar playing its own source keeps Play/Pause for itself (see "The bar on its own").
- TalkBack hears the change once, when the shown state moves: "Reconnecting to the TV…", "BRAVIA 8 unreachable", then "Connected to the TV again"; never on a blip, never at the first connect. The card's change is its usual opacity fade-through, which is also the reduced-motion form; the ring stops turning under reduced motion, as before.

- **« Bluetooth de secours »** ("Backup Bluetooth") on the TV row opens a short pairing step, a dialog: one line saying what it is for (the remote reaches the TV over the phone's Bluetooth when the network drops: keys, touchpad and keyboard), then the state in words with its one way forward (« Pas encore associé » with « Rendre visible »; Autoriser, Activer, Réessayer; « Associé à la TV » or « … et connecté »), the TV's steps while not paired (Paramètres › Télécommandes et accessoires › Associer un accessoire, choose tutti, confirm the code), and once paired the TV's keyboard layout (QWERTY US or AZERTY French, with why it matters) and « Oublier ». The first host that connects while it is open becomes the TV's link, never a computer. « OK » closes it. No trackpad, pointer or keyboard in Settings.
- **The one-app-at-a-time note** sits where it matters: at the foot of the pairing step, and in the Connexions sheet's Bluetooth line when another app holds the role (« pris par une autre app : une seule à la fois peut servir de clavier »).
- Computers pair through « Ajouter un appareil », as before.

### Devices, stage 1 (Maya, 2026-10-25)

**Any computer, not only a Mac (Erwann, 2026-10-25).** Wherever this section and the bullets above say "the Mac", read "the computer": the kind is « Ordinateur » with a system, macOS, Windows or Linux.   - Actions are text buttons under the status, each its own 48 dp target, wrapping in French. Mac: Renommer, Entrée HDMI (radio list: each HDMI input with « un appareil branché » / « rien de branché » in words, then « Aucune entrée (AirPlay seulement) »), Disposition du clavier (Français Apple by default, or Américain (Mac), with why it matters), Associer à nouveau, Oublier l'appareil (confirmation naming the Mac, and saying the phone must also be removed on the Mac to unpair fully).
  - The separate Settings › Bluetooth group is gone: it only ever paired the TV, which is now the TV row's job. The Bluetooth screen and its stack key are gone too (above).
  - « Ajouter un appareil » is the one way in, always shown. Full screen, Back steps back. ## Quick access (v1)
Quick Settings tile (opens a compact remote overlay), phone volume buttons drive the bar while the app is in front (and while the notification shows, below), home-screen widget (scenes + volume), media-style notification.
- The widget says what's on, never "Connected" (Iris's design idea 4, Erwann approved 2026-10-25): its top line is the now-showing card's state in the card's words, after the state's glyph ("YouTube · Cinema", "HDMI 1", "TV on standby", "TV out of reach"; the active scene follows what plays, never a standby), and without a TV the soundbar by name or "Bar 9 unreachable" (`quickHeadline`, tested). Play/pause sits at the end of that line, 36 dp so the medium widget keeps its two rows, and joins the volume row on a one-row widget from 240 dp wide; it is the TV's, greyed only while the TV sleeps (`playPauseOffered`); out of reach a tap connects like volume does and the TV-link rules hold or drop the key. The widget picker shows a real preview, `layout/quick_widget_preview.xml` (the medium widget with example content), through `previewLayout` on Android 12+ and as the generated preview on Android 15+ (`QuickWidgetPreview`, once per version, the call being rate-limited); Android 10 and 11 still show the loading layout.
- State on the quick surfaces follows the remote's rules (Iris, 2026-10-24): the tile's subtitle and the widget's number show the volume rule's level only once it is reported ("Connected" or "–" until then, never "Volume 0"); the widget's active scene pill wears a tick and bold type as well as its full fill, and TalkBack reads it as "Cinema, active"; once changed by hand it drops the fill and the tick and reads "Cinema · modified", as the remote's pill does. TV settings already show no value while the TV's IP link is down: the screen is the link's explainer until it is back.

### Lock screen
- Iris's design idea 9 (Erwann approved 2026-10-25): turning the bar down at 23:00 with the phone locked in hand is the urgent gesture, so it no longer asks for the unlock. The Quick Settings tile opens its overlay over the lock screen (`setShowWhenLocked`, only when opened locked) with what is harmless in anyone's hand: what's on, play/pause, the volume rail, − and +, mute, and the phone's volume keys; the rail still stops at the cap and at the high-volume guard, which it can't ask past. Power and scenes wait for the unlock, and one quiet line says so ("Unlock for Power and scenes"); they appear as soon as the phone is unlocked, live. "Open the remote" asks for the unlock first (`requestDismissKeyguard`). The media controls keep previous, play/pause, next, mute and the volume keys on the lock screen, and gain Turn off behind the unlock (below).
- The overlay's line says what's on in the widget's words (`quickHeadline`), after the state's glyph instead of a coloured dot; play/pause sits before Power, greyed only while the TV sleeps.

### Media controls
- A media control, not a notification (Erwann, 2026-10-25: « Je ne suis pas sûr de vouloir une notification ; en tant que contrôle je préfère un format média, pour l'avoir dans le lecteur média intégré d'Android »): the room lives in Android's own media player, the shade's media carousel and the lock screen's media controls, through one MediaSession and a MediaStyle notification that carries its token and nothing else; there is no second, ordinary notification for the same controls. The session is owned in one place (`QuickNotifications`); whatever learns what is playing (Maya's Cast "now playing") feeds `QuickState.playback` (title, artist, paused, position, length, whether an absolute seek can be sent) and never opens a session of its own. The switch-off timer keeps its own small notification.
- Media style, backed by a MediaSession (`quick/notification/`; rules in `MediaCard.kt`, unit-tested). Shown while the TV is on, the room's link is up and the setting is on; Android 13+ also needs POST_NOTIFICATIONS. Once shown, a dropped link (the sessions stopping behind the app, Wi-Fi going) no longer removes it: it keeps the last known state (`shownCard`, tested), and every button and the volume keys reconnect through the controls' held path before acting. It goes when the TV is reported off on a live link, when the setting is turned off, or with the process. No foreground service: it mirrors the controller, it does not keep it alive.
- Title: what is playing when reported (`playback.title`), else the TV's foreground app ("YouTube"), else the active scene, else tutti; with a reported title the line under it is the artist and the app. Text: the configured devices, then whose level it is: "BRAVIA 8 · Bar 9 · Bar vol. 10". Large icon: the app's cached icon, else tutti's mark. Lock screen: public; nothing on it is a secret.
- Artwork (Iris, 2026-10-26; Erwann saw the 192 px icon stretched blurry over his whole lock screen): `METADATA_KEY_ART` is its own picture, drawn on device (`MediaArt`, tested; `MediaArtwork`), never the small icon scaled up. Square, at the size the framework keeps (320 dp, 512 to 1024 px), so the player's wide crop and the lock screen's tall crop both keep the middle: tutti's ground (#1C1B22), one soft dithered radial glow in the app's colour (the brand's fill, else the icon's mean, else tutti's amber), as strong as it can be while white text over its brightest point keeps 7:1 for the clock and the title, and the app's icon crisp in the middle at 16% of the side (a banner at its own shape, 28% wide; tutti's mark in a 40% box), modest because a lock screen that crops the square tall magnifies it about 2.2 times,, rounded like the launcher; the phone's own copy of the app first, then the TV's, then the brand logo; with nothing known, tutti's remote glyph on its amber glow. No text, nothing told by colour, nothing fetched (Cast thumbnails stay out until Erwann says otherwise). Redrawn only when the app or its icon changes, never on a volume tick. The small icon stays as it was.
- One volume rule for every quick surface: the bar when one is configured, else the TV. A level not yet reported is unknown and left out, never shown as 0; the TV's remote link reports `0/0` while its sound goes to the bar, so a TV level with no range is unknown too.
- Buttons, in the media player's own layout: previous, play/pause and next, the TV's media keys over the remote link (the TV-link rules apply: play/pause waits for the link's return, skips are dropped with a reason), then mute and Turn off as the session's custom actions. Mute shows the state (struck speaker while muted); its label says what a tap does. Volume has no buttons: it is the session's remote VolumeProvider, so the phone's keys and the system's media volume slider drive the bar's level, stopped at the cap and at the high-volume guard like every quick surface. Collapsed (Android 12 and older): previous, play/pause, next. The TV does not report play/pause, so the session reads "playing" (the button a toggle) unless `playback` says paused; a progress bar shows only with a reported position and length, and seeking only where `playback.canSeek`.
- Turn off (Iris's design idea 9, Erwann approved 2026-10-25): a fifth button, last and only in the expanded player, switches the room off (TV and bar; off only, never a wake: `QuickControls.powerOff`), and only once the phone is unlocked, since the lock screen is anyone's hand. The notification's button is an activity (`QuickTurnOffActivity`, no window), so the platform asks for the unlock before starting it, with `setAuthenticationRequired` on Android 12+; if it still lands over the lock screen it asks itself through `KeyguardManager.requestDismissKeyguard`, and a cancelled prompt sends nothing. Android 13+ draws the controls from the session's custom actions, which run without any unlock, so there Turn off joins them only while the phone is unlocked (`turnOffInSession`, from a lock watcher on the screen-off, screen-on and user-present broadcasts) and comes back with the unlock; a tap racing the lock is dropped. Previous, play/pause, next, mute and the volume keys keep working on the lock screen, the high-volume guard still stopping the volume on its line.
- Volume keys: a remote, absolute VolumeProvider (0..the bar's cap, or the TV's max) makes the phone's keys drive the bar (or the TV) whenever the notification shows (Erwann, 2026-10-24, answering the long-pending question). Android sends keys to the most recent playing session, so a phone app playing its own media takes them back while it plays; with nothing playing on the phone, the keys stay on the room, ringer included, lock screen included. If that proves too eager, the narrower scope (only while tutti is in front) is one switch: `VolumeKeysScope.IN_FRONT` in `QuickNotifications`, which then needs an app-in-front signal.
- Posts are held 400 ms apart, trailing, and an unchanged card is never re-posted: Android silently sheds updates past about five a second, and the shed one can be the last.

## Visual
- Material 3 Expressive, restrained: dynamic colour, springy shape changes, big rounded targets. Expressive in motion, not decoration.
- Dark first: near-black surface, optional true black for OLED, no white flashes. Light theme secondary.
- Pad: one large quiet surface, no grid lines, the same rounded rectangle (36 dp corners, surface-container-high) in both modes, so the D-pad and the touchpad are one size and switching never grows or shrinks the control (Erwann, 2026-10-24). D-pad mode puts a disc on that surface a tone up (surface-container-highest), as wide as the surface's short side allows, with a chevron at each point and an OK centre set off by a thin moat. Only the drawn disc answers (Erwann, 2026-10-24: "on devrait activer les flèches que quand on touche les flèches"): OK in the centre zone (a tap is OK, held is the TV's OK held: Gestures › OK held), otherwise the direction of the quarter between the diagonals, out to the disc's edge; the surface round it is inert in D-pad mode, and the switch's corner only switches (`dpadZone`). The one under the finger lights its quarter of the ring until release. Volume second loudest. Everything else tonal, not outlined.
- Haptics are primary feedback: light tick per D-pad/swipe step, firmer click on Select, soft bump at volume limits/cap, double pulse when a scene finishes.
  - Volume detents (Iris, 2026-10-25): a volume move that arrives on or jumps over a landmark plays a detent instead of its tick, so a level is found blind, in the dark. The landmarks are the three saved levels, the high-volume guard's line while the guard is on (locked or not: it still marks where loud starts) and tonight's cap (`VolumeRules.landmarks`, `TuttiUiState.volumeLandmarks`). Leaving a landmark is not crossing it, and a fast drag that skips levels still finds the one it jumped over (`VolumeSteps.crosses`, tested). A wall stays the bump: when the guard stops the rail on its line or the cap is the ceiling, the bump and the stretch say it, never a detent. The detent is `SEGMENT_TICK` (API 34+; `VIRTUAL_KEY` before), firmer than the step's frequent tick and distinct from the bump; it is kept under "Essentials only" (a landmark, not chatter), dropped when vibration is off, and Android's touch-vibration switch applies on top as for every haptic (`performHapticFeedback`). It plays on the rail (drag and + / −), the pad's two-finger steps and the volume sheet's stepper and slider. Not yet on the Quick Settings overlay's slider, which reads `QuickState`, not the app's state.
- Numbers that change under a finger use tabular figures (`TextStyle.tabular()`, `ui/common/Digits.kt`, Iris, 2026-10-25): the rail's level, the volume sheet ("Now 18", the stepper, "Set to 24", the saved levels, tonight's cap), the overlay's level, the pad's "Vol 24" tag and the guard's stepper, so 18, 19, 20 hold their width while a drag runs through them. The widget (Glance has no font features) and the media notification (the system draws it) keep the platform's figures.
- Motion: springs under ~250 ms; reduced motion → fades.
- Launch: the system splash shows the splash lockup still, the launcher mark over the lowercase "tutti"; an in-app intro (`ui/intro/LaunchIntro.kt`) takes over at the same place and size and the OK becomes the pad: it warms and slides onto the D-pad's OK while a shimmering ring runs out and morphs into the pad's surface, the disc filling on it, or, in touchpad mode, to the touchpad's centre while the ring morphs into the pad's rounded rectangle and the OK sinks into the surface. The word is on the very first frame (Erwann, 2026-10-24: "pourquoi tutti est pas affiché au début aussi"): it is baked into the splash icon (`splash_icon.xml`), the one picture both Android 12+'s splash and core-splashscreen's compat splash on Android 11 show, rather than `windowSplashScreenBrandingImage` (12+ only, at the bottom of the screen) or a word that pops in with the intro. Both splashes draw the icon's 108 units over 288 dp and show only a 192 dp circle of it (36 units round the centre), so the lockup is the mark at 0.65 with its middle on the centre and a 58-unit word 10 units under the handset, reaching 34.8 of those 36 units: on screen the handset is about 100 dp tall and the word about 100 dp wide (x-height about 27 dp), smaller than the old mark-only splash (155 dp) so the name fits. The intro places itself on 288 dp centred on the splash's icon view, whatever that view's size (288 dp on the compat splash, the 192 dp circle on 12+), so its first frame is the same lockup at the same place. On a cold start the intro then holds PR #11's splash composition (Erwann, 2026-10-24: "oui, fais-le avec le mot et le halo", then "le splashscreen est trop rapide"): the lockup never moves, and on a dark splash a soft halo in the theme's accent (peak 0.16, dithered, no banding; none in light, as in the study) breathes in behind it over 300 ms. The hold lasts until the lockup has read for about 1.2 s since the launch, the system splash's own time included, never less than 600 ms nor more than 1 s in the app; it runs while the intro waits for the stores and the remote's layout, so a slow load eats into it instead of adding to it. Word and halo leave over the choreography's first 160 ms, before the body steps back. Reduced motion: the same hold (the halo only changes opacity), then the fade takes the lockup with the mark. A warm start has no hold or halo; its word, on its splash too, leaves with the first beat. Nothing of it is announced. A click and a bloom on landing, then the backdrop opens onto the remote, already drawn underneath. The light (halo, rings, sheen, bloom) is the theme's own colour, soft and low, never white or a fixed amber. 800 ms cold, 300 ms warm, none on a resume; the first launch hands the mark to the welcome screen; reduced motion is a 200 ms fade; a tap skips it. Ivory on ink in dark, ink on ivory in light. The mark (Iris, 2026-10-24, from the v2 brand study, PR #11): a tall ivory handset (34 x 58 in the 108 viewport), a small top button, one ink OK and an amber pill, flat, inside the 66 dp safe zone; one geometry (`ui/intro/MarkGeometry.kt`) for the launcher foreground, the themed (monochrome) icon, the system splash and the intro, checked by `MarkGeometryTest`. Kept from v2: the proportion, the top button, the heavier pill. Not kept: the dial ring round the OK (two inks at about 1.6:1 vanish at 48 dp, and the intro's one moving part is a single OK), gradients and drop shadow (the launcher adds its own depth), the amber glow (now the intro's halo, in the theme's accent), and v2's palette nudges (ivory `#F4EFE7`, amber `#E5A14A`: below what the eye separates; `design/branding/README.md` stays the palette).
- Colour without Material You (Android 11 and below): Material 3's baseline scheme, which Erwann preferred to a brand scheme (2026-10-24). Android 12+ keeps dynamic colour. Either way, messages, menus, sheets and the window draw from the scheme in use, never from system defaults.
- Messages and popups (Iris, 2026-10-24): nothing tutti shows comes from the system's own look.
  - No `Toast`, no default snackbar. A passing message is tutti's message (`ui/common/Messages.kt`): a tonal card in `surfaceContainerHighest` with `onSurface` text, the theme's large shape (16 dp), bottom centre above the navigation bar, at most 560 dp wide; never the inverse colours, which flash a light bar over the dark remote. A leading glyph says its kind (info, or the warning triangle for a problem, which TalkBack also reads as "Problem"), a close button, and an optional action ("Show me how", or "Copy details" in developer mode) on its own line under the words, end-aligned: beside them it squeezed a long message into a narrow column. One at a time; a new one replaces it. 4 s, or 8 s with an action or for a problem, stretched to the user's accessibility timeout. It rises 16 dp on a spring and fades; reduced motion is the fade alone. It is a live region (polite, assertive for a problem) with a dismiss action.
  - A message is one short sentence (Iris, 2026-10-24, after the wake-failure message filled six lines of a narrow card): what happened and, when it helps, the one next step, as "what: do this" with no full stop. Aim at 12 words; the hard cap is 14 in every locale, counting only words with a letter or digit, so French's spaced colon is free. 14 is three lines of the card's text column on a 360 dp phone, read in a glance inside the 4 s a plain message stays, and leaves French its usual 15% over English. A problem says what to do, not only what failed ("The TV did not wake: turn on Remote start", never "Wake failed"). Anything longer goes behind the message's action: "Show me how" opens the Unlock checklist at the step that holds the menu path and the why; with no such place, the action opens a dialog that holds it. The technical cause is never in the words: developer mode's "Copy details" carries it. Same voice as the rest of the app, French in vous, the kind told by the glyph, never by colour alone. `MessageCopyTest` holds every message string and fails on one over the cap; a new message string joins its list.
  - A dialog's title says what is at stake ("Forget this device?"); its body is at most two short sentences, or steps as a numbered list, one action a line, with Sony's menu names as on the TV and the same path as the Unlock checklist.
  - The host sits at the app root, and every `TuttiSheet` carries its own, since a sheet is a window above the root; only the topmost host draws. A dialog confirms in place instead (the crash dialog's Copy becomes "Copied" with a tick).
  - Menus go through `TuttiMenu`: medium shape (12 dp) on `surfaceContainerHigh`. Dialogs are Material 3's own, drawn from the theme.
  - A failed action offers "Try again" in the button's normal tonal dress with a retry glyph; the failure is told by the shake, the reject haptic and the warning line under it, never by a red button with a ✕ (which reads as cancel).
  - The refusal shake (Iris, 2026-10-25, answering Erwann's « faire trembler le bouton en cas d'erreur ? »): one shake for the whole app, `Modifier.refusalShake` with `rememberRefusalShake()` (`ui/motion/RefusalShake.kt`), played by `refuse()`, which also plays reject on the same frame. It goes with the reject, never with the bump: only when a command that was sent came back refused (the bar's ERR or NAK on a Sound tile or a pin, a wrong pairing code, a progress button's failure), on the control that was pressed, since that control looked available and the shake is what ties the failure to it. A control already in the down dress, refused at the tap, bumps and does not shake: its dashed ring said so first and the system chip carries the cause; a guarded key, the guard's stop on its line and the volume walls are not errors either. Sideways only, never scale or rotation: +A, −A, +0.6A, −0.4A, 0 at 40, 100, 160, 210 and 250 ms (`Motion.MEDIUM`), linear between keyframes, no spring; A is 4 dp on controls up to about 96 dp (keys, pins, tiles, segments) and 6 dp on fields and wide buttons (the pairing code, "Try again"). At most one shake per control every 600 ms; a refusal inside that window plays its haptic but does not restart the shake. Never on the pad, the rail, a whole sheet or the screen. Reduced motion: no travel, the control dips to 50 % opacity and back over `Motion.SHORT`, once; the haptic and the message stay. `rememberReducedMotion()` follows "Remove animations" live (a `ContentObserver` on the animator scale). Nothing is added for TalkBack: the assertive message already says it.
  - The XML theme follows the system's day and night (`values-night/themes.xml`), with the brand's window and accent colours, so framework-drawn pieces (text selection, a window before Compose) match. - Glyphs (Iris, 2026-10-25, from Erwann: "des icônes monochromes sur les options quand ça vaut le coup"): options wear a monochrome glyph when it helps recognition; never for state (state has its own small marks, below), never a brand on an option; a source that is a brand (Spotify) wears its own Simple Icons mark, monochrome. - App faces (Erwann, 2026-10-25: "fais des icônes tout en couleur partout, mais faut que ça prenne toute la place du bouton", and "dès que tu as des logos, mets-les en couleur"; Iris on the tiles).   - On has one dress across the app: the accent fill (`primary`), squarer corners, and a mark that is not colour: a check (Dock pins, Sound tiles), the slashed speaker (Mute), the power glyph on its accent disc (Power). Off is the same control in its plain dress, with an empty ring where a check would be. Not known is a dashed ring or dashed outline, never the off dress.
  - Tonal fills are families, never states: the round keys wear `secondaryContainer` because they are the remote's fixed keys, always there and always the same; every pin, Apps and Keys included since 2026-10-28, sits a tone quieter (`surfaceContainerHigh`) because they are his and change. Neither ever wears a check or the accent fill unless it is a toggle that is on.
  - Scene pills keep their own colour, chosen per scene so each is found at a glance: identity, not state. An idle pill is a pale tint of it; the active one is filled with it and carries a check (and TalkBack's "Active"); changed by hand, an outline and the word "modified". The check, not the tint, says which is active.
  - Choices (DRC, IMAX, bar input) are selections, not toggles: one outlined row of segments, the chosen one filled and ticked (on the bar input, the tick takes the icon's place), every option in view, read as radio buttons.
  - Gauges (the volume rail's fill, a scene's progress) are amounts, not states.
  - Read-only is not disabled (Iris, 2026-10-27, from Erwann on About this TV: « Que ça soit disable ok mais pourquoi le cacher ? »). Information the app only shows (the TV's model and API generation, the bar's raw values, the current input, a row that heads its own buttons) keeps full `onSurface` / `onSurfaceVariant` contrast and has no chevron, ripple or click semantics: a `SettingsRow` with no `onClick`. The faded look is only for a control that is genuinely unavailable, and that control always says why in words (a `notice`, the down dress's reason). Never `enabled = false` on a row to mean "nothing to tap".
  - Binary and link states wear a leading mark whose shape differs (Iris, 2026-10-27, from Erwann on Inputs: « on devrait mettre des check etc. »): a filled check circle (`ic_check_circle`) for connected, on, paired or ready; an empty ring (`ic_circle_outline`) for nothing connected, off or not paired yet. The current input is the filled check plus "Current input" / « Entrée actuelle », shown only when the TV reports which input is current. The words always stay beside the mark; the mark is decorative to TalkBack. One composable draws it (`StateMark`, `ui/common/SettingsCards.kt`, or `SettingsRow(mark = …)` to lead a row's detail), the same two glyphs as `ConnMark`'s OK and TODO in the Connexions sheet, whose fuller set (↻ on its way, ☾ standby, ⚠ needs a look) stays for links that can be in between. Never colour alone: Erwann is colourblind.
  - Down has one dress across the remote (Iris, 2026-10-25, from Erwann's "pourquoi quand c'est pas connecté et en train de connecter le statut des boutons n'est pas le même, et surtout ce ne sont pas tous les boutons ?" and "non connecté ou en cours de connexion ça devrait être pareil, genre disabled"). A control whose device's link isn't up, connecting or out of reach alike, loses its fill and wears a dashed ring in the outline tone, its glyph in onSurfaceVariant (`drawDownRing`): the round keys, Keyboard, the mic, the Dock's pins. The pad keeps its surface, so the big area reads as waiting rather than broken: a dashed edge runs round it and its chevrons, OK and mode switch dim to 38%. Shape says it, never colour alone; it changes by opacity, which is also its reduced-motion form. A tap on a down control bumps, nudges the system chip (which says why) and sends nothing; a down pin's long press still opens its menu and the editor. TalkBack reads the reason as the state: "Connecting to the TV" or "BRAVIA 8 unreachable" (the bar's: "Connecting to the bar", "Bar 9 unreachable"); the pad, down, is one node with no actions. Keyboard never wears its "on" look while down: a field remembered from before the drop is not a field now. All keys follows it too (Erwann, 2026-10-25, from a dev screenshot whose bar said "Connecting…" over a sheet of live-looking keys): every key in it is a TV key, so with the TV down every key wears the dress, the colour swatches dim to 38%, the reason heads the sheet as on the playback sheet, a tap bumps and sends nothing, and the long press refuses "Pin to dock" with a bump, as the Sound sheet's pins do while the bar is down.
  - Per device, never "anything down disables everything": TV controls follow the TV's shown link (`TvLinkRule`, so a blip under 3 s stays normal), bar controls (Mute, the bar's pins) follow the bar's. With the TV out of reach and the bar connected, volume, Mute, the Sound sheet and the bar's pins stay normal. Power, scenes and macros never go down: they wake the TV, which is exactly when it is out of reach, and a scene runs its bar steps whatever the TV does. Power pins count as Power. A device not added has nothing to wait for and stays normal. Rule in `controlLink` and `dockOwner` (`ui/remote/ControlLink.kt`, tested).
- Performance target: visual and haptic response within one frame of a tap, before any network round trip.
- UI in English by default (`values/`), French as a translation (`values-fr/`); every string in both.

### Salle obscure: the phone dims with the room (Iris, 2026-10-25, benchmark)

Settings › Display & feedback › "Salle obscure" ("Dark room" in English), off by default. From 20:00 to 05:00, while the TV is known on and tutti is in front, tutti's own window fades to a low brightness over about 2 s (0.03 of the window's scale, which is linear in light: about a third of the way up the system slider, some 15 nits on a Pixel, legible in a room lit by the TV; Iris, 2026-10-26, down from 0.12, which sat near the slider's middle and could brighten an evening phone), and never brightens: with manual brightness already at or under that level it does nothing, and back up over the same 2 s when the TV goes off, the switch goes off or the evening ends (`dimTarget`, `EveningDim`, tested; `EveningDimmer`). tutti never writes the phone's brightness setting, only its window's: so the moment he moves the system brightness, the window lets go at once and stays at his level for the rest of that evening, the evening after midnight included. With Android's animations off the fade is a jump. Under adaptive brightness his level can't be read, so the dim applies as is. Unverified: whether auto-brightness on some phones writes the same setting, which would read as his change and end the dim early.

## TV settings: Sony's menu, in words (Iris, 2026-10-26)

Erwann, on the screen fed by IP control: « We need to improve that it's from IP.control »: it listed the TV's targets alphabetically, raw (`advContrastEnhancer`, `medium`), with the reason a row was unavailable crushed into its title. Now:

- **A hub, then a screen per part (Iris's settings proposal, approved by Erwann on 2026-10-26: « Ok pour les trois décisions d'Iris »; `docs/proposals/settings-structure.md`).** It replaces the Advanced fold of the same day (Erwann: « advanced devrait être un second screen plutôt qu'un collapse »). Settings › TV opens a hub: Picture, Sound, Inputs, Power, About this TV, in Sony's order, each a row with its icon, its name and one live line saying where it stands in words ("Standard · brightness 32", "Audio system · Standard", "HDMI 2 · 4 inputs", "Power saving: Off · Wake-on-LAN on"), never a colour or a dot. A part with nothing to show has no row. The hub opens at once and the load starts on the way in (moving between the hub and its screens asks the TV nothing new; IP control coming back while any TV screen is open reloads); a part still on its way says "Waiting for the TV…" on its row, and inside its screen the waiting rows hold their places. Without IP control, the hub and every screen under it show the explainer instead. The top bar's arrow and system back go up one level (`TvHub`, tested; `Screen.TvSettingsPage`).
- **Picture keeps the handful people reach for** (`TvSettingCatalog.everydayTargets`): picture mode, the TV's scene select right under it, brightness, contrast, colour, colour temperature, Motionflow. Its last row opens **Advanced picture · N settings**: one screen, no fold, everything else under Sony's sections as headings, in its order, so anyone who knows the TV's menu finds a setting where the TV keeps it: Automatic picture, Brightness (gamma, black level, peak luminance, local dimming…), Colour, White balance, Colour adjustment, Clarity, Motion, Video options, Other. Not a screen per section: that would be a fourth level for groups of three to eight rows. A target the catalogue doesn't know lands last, in "Other picture settings", under the TV's title or its raw name, with a line saying so.
- **The XR80's leftovers (dev.14 screenshot, 2026-10-26)** have their place: `redOffset`, `greenOffset`, `blueOffset` (-20 to +20) join White balance after gain and bias ("Red offset", « Décalage du rouge »); `sensorAutoAdjustment` follows the light sensor ("Light sensor auto adjustment", « Réglage auto par le capteur de lumière »); `contentType` ("Content type", « Type de contenu », values Video « Vidéo », Graphics « Graphiques ») sits in Video options. Where Sony's own XR80 menu shows these three is unverified: no XR80 menu was in reach, so the places follow the nearest documented setting.
- **Loading says what it waits for, and keeps what is known (2026-10-26).** Erwann: "when it's loading it's not clear as we already have some result". On dev.14 the screen opened with Inputs alone under a thin progress bar, then everything landed above it at once. Now the load lands part by part as the TV answers (`TvSettingsState.waiting`: picture, then sound, then power), and on the first load each part still out holds its own place, under its own header, with a row naming it and "Waiting for the TV…" beside a small spinner (a still glyph under reduced motion). Under the bar, a line in words: "Asking the TV for its settings over IP control…", and "What the TV already told tutti is shown as it is.", read politely by TalkBack. What tutti already knows shows final from the start: the picture mode (it rides the remote's own poll), the inputs, the device. A re-check over settings already shown (every way into the hub, IP control back after a drop) is quiet (Iris, 2026-10-27, after Erwann's « pas très fan du loading là » on dev.27): what is shown is valid, so no bar, no sentence, no waiting rows, nothing that dims the rows or pushes them down; under 1 s nothing shows at all, past it a small spinner sits in the top bar's actions (the refresh glyph, still, under reduced motion), fading in and out by opacity, named "Checking the TV's settings again…" to TalkBack, and values that change simply update in place (`TvHub.loadCue`, tested). The loud form is for waiting on something missing, never for confirming something shown. The waiting state never rests on colour or motion: the words carry it. The early values come from IP control's own poll, like the rest; Google TV's remote link carries no settings.
- **Words for every target and value** in both languages (`TvSettingWords`, tested): Sony's menu names where they exist; per-colour targets compose their colour and part ("Blue gain", « Gain du bleu »). A value tutti has no words for uses the TV's title, else is made readable (`warm1` → "Warm 1").
- **Unavailable rows are hidden by default**, behind "Show unavailable settings" at the foot of each screen that has any (Picture, Advanced picture, Sound), whose line counts that screen's own ("12 unavailable with the current input or mode"); it starts off each time a screen opens. Shown, they stay in their place, faded, with the reason as their own line in words, never a fade alone. They change with the input, so they can't be hidden for good.
- **Sound and speakers too** (Erwann, 2026-10-26: « Mets aussi le son de la barre en mots clairs »): `arrangeSound` orders them as Sony's menu (output, sound mode, then TV position and the subwoofer's level, frequency, phase and power), unknown targets after in the TV's order with the same "Named as the TV sends them" line, unavailable rows behind the same switch. The group reads "Sound output" while that is all the TV lists, "TV sound" once it lists more. Values have words (table-top stand, wall mount, normal, reverse). A scene's picture mode uses the same words, in its summary and its picker.
- **The bar says no raw word either**: a choice value outside the documented vocabulary is made readable, never shown as sent; Technical details names the bar's network mode, DHCP, connection type and internet state (wired, Wi-Fi, connected, on, off), and names refused features by their labels. A word tutti doesn't know is still shown as the bar spells it: those vocabularies are unverified on the Bar 9.
- **A slider row** gives the title its own line: the value sits beside it only while it can change, and the reason goes under it. The two ends of the range sit under the slider, and ranges either side of 0 sign their positives, so a thumb at an end reads in numbers: Sony's gains top out at 0, which looked like a bug.
- **Short choices are segments, not a menu (Iris, 2026-10-26, after Erwann's « Pour des options comme ça on peut mettre un segment nan ? » about Power saving).** A choice with two to four options shows them all as one outlined row of segments under its name (`OptionsRow`), the chosen one filled with a tick above its name, so it never rests on colour; every name may take two lines but no word may break, measured in the language, width and font size on screen (`SegmentFit`, tested). Anything that doesn't fit (five options, « Image désactivée » on a narrow phone, a large font) keeps the menu rather than ellipsising. Unavailable, the segments are disabled with the reason under the name; a tap is optimistic and a failure moves the tick back with the reload; TalkBack hears the setting, then each option as a radio button. The TV's write-only sound output keeps its menu: with no current value there is nothing to tick.

## The phone keyboard covers nothing that matters (Iris, 2026-10-28)

After Erwann's « Certains screens sont coupés car on doit scroller alors qu'on a la place » (the pairing code's count hidden under Gboard with room to spare). The rule, in `ui/common/Ime.kt`, for every screen and sheet with a field:

- One owner per inset: a Scaffold's padding is consumed before `imePadding()`, since the keyboard's inset already holds the navigation bar; sheets pad by the larger of the two (`TuttiSheet`). Counting the bar twice cost 24 to 48 dp.
- While the keyboard is up, decoration shows only if everything still fits (`roomWhileTyping`, its sum in sp so it follows the font scale): the code step's TV drawing and the search step's radar yield, the words around them already say the same. Without the keyboard nothing changes. The size change is an expand or shrink with a fade; reduced motion fades only.
- The focused field's whole group, the field with its counter or helper and its action, is brought into view as the keyboard settles (`keepAboveIme`), not the field alone. Scrolling stays, as the fallback.
- The onboarding's back arrow shares the "Step 2 of 4" line instead of a row of its own. TalkBack still reaches it alone, then the bar as one description.

Each thing has one name in each language, everywhere: screens, TalkBack, the notification and the widget.

- IP control has one menu path, written the same in every string, as Sony's guide and the IP control dialog give it: Settings › Network & Internet › Home network › IP control (FR: Paramètres › Réseau et Internet › Réseau domestique › Contrôle IP). Menu paths use ›.
- `WordTableTest` fails on a banned word in either locale (téléviseur, télé, applis, Alimentation for the control, Slot, Put in the dock, another IP control path), naming the house word; its probe proves every pattern still catches its example.
- Link states in French are invariable (« en ligne », « injoignable », « à configurer »), so they agree with any device: « télécommande en ligne », « barre injoignable ».
- Counts use plurals in both languages; French `one` covers 0 and 1.
- Failure marks are `ic_warning`, never ✕: ✕ means close or remove.
- Every choice in a picker is a 48 dp target with a name TalkBack reads; a chosen colour also wears a tick.
- Landscape is supported, not locked: the app pads the display cutout's sides, so no control sits under a camera hole. Indeterminate bars (`BusyBar`) stand still at a third under reduced motion, like the spinners' still arc.
- The Forget dialog names the device it forgets.

## Updates (Maya, 2026-10-27)

- About › Version is one row: the installed version, and under it where the updater stands, in a sentence ("Check for updates", "Version 0.2.0-dev.26 is available.", "Couldn't reach GitHub…"). Tapping it checks and opens one sheet: the state as a sentence (a polite live region), one button for the next step (Download and install, Open the setting, Try again, Check for updates), a progress bar while it works, and the rule in small print: GitHub when asked, at most once a day on opening, nothing installs without confirmation.
- A newer build makes itself known without nagging (Iris, 2026-10-28, from Erwann: « l'update via GitHub devrait être plus obvious »; he installs dev builds several times a day). Three places, each quieter than the last:
  - **The first time a build is found**, one message, once per build: "Version x is available." with **Install**.
  - **Until "Later"**, the remote's ⋮ wears a dot: an 8 dp disc in the primary colour, cut out of the glyph by a ring of the background, top-right of it. A shape in a fixed place whose words are one tap away, never a colour on its own; TalkBack hears "More options, update available". Nothing on the remote's surface moves: no banner, no change to the pad's room.
  - **While a newer build waits**, the ⋮ menu's first row is "Install version x" (download icon; it repeats the dot while it notices, which ties the dot to its words), and Settings › About's line reads "Version x available".
  - **Install** and the menu row are one tap: the update sheet opens over the current screen and starts the download at once (checking GitHub first if this run doesn't hold the build); Android's own confirmation is the only other step.
  - **"Later"**, under Download and install in the sheet, sets that build aside: the dot goes, the menu row and About keep it. A newer build than the one set aside notices again. The message never repeats for a build already found.
  - **When it checks**: on opening and on coming back to the app, at most once an hour for a dev build and once a day for a final release (`CheckSchedule.intervalFor`), never in the background. No notification and no notification permission: the person who installs builds is the person holding the app open.
  - The GitHub updater is meant to be temporary (final releases will likely go to F-Droid), so the rest of the app reaches it through three entry points in `ui/about/UpdateSection.kt` only: `rememberUpdateCue()`, `UpdateCheckEffect` and `UpdateNowSheet`. A build without it makes those return nothing; the remote's menu and Settings take plain values.
- Failures say what failed and what to do; no state rests on colour.
