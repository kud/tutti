# Architecture

## Modules

```
:protocol  pure Kotlin/JVM. Codecs, state machines, reducers, clients over abstract transports.
  net/      Connection, TcpConnector, TlsConnector (TOFU pin), CertificatePin, LanAddress, LineSplitter, Redact
  theatre/  soundbar TCP 33336: TheatreCodec, TheatreReducer (optimistic), TheatreClient
  atv/      Android TV Remote v2: Wire protos, Framing, PairingHash, PairingMachine, AtvPairing,
            RemoteSession, AtvRemote, VoiceSession, KeyMap, AppCatalog, ClientCertificates
  bravia/   REST JSON-RPC + the code's cookie or the PSK: JsonRpc, BraviaParsers, Capabilities, BraviaClient, IpRegistration, Ircc
  grpc/     Sony-cloud plane: interface, field paths, PKCE, UnavailableSonyCloudPlane
  scenes/   Scene model, SceneEngine (plan / match / capture), SceneRunner, StarterScenes
  cast/     Google Cast v2, read-only now playing: cast_channel proto (Wire), CastFraming, CastDeviceAuth,
            CastRoots, CastStatusParser, CastStatusReducer, CastSession
  hid/      Bluetooth HID: HidDescriptor, HidReports, KeyLayout (US, French AZERTY), MotionAccumulator,
            TouchpadMotion, AirPointer (gyro pointer)
:app       Android: Compose UI, Hilt, DataStore, Keystore secrets, socket/TLS/OkHttp transports
```

`:app` owns sockets, TLS, HTTP, reconnection and lifecycles; `:protocol` owns bytes and state. Every client exposes a `StateFlow`; every write updates state before the network round trip, so the UI and haptics respond within a frame.

The quick surfaces (tile, widget, notification) read `QuickControls`, a narrow slice of the controller. The notification owns a framework `MediaSession` (no androidx.media dependency) on the process-wide `QuickRuntime` scope: it exists only while the notification shows, carries a remote `VolumeProvider` that routes the phone's volume keys to the bar (or the TV) through the same `QuickControls`, and dies with the process. No foreground service; see design.md, "Notification".

## Protocols

### 1. Android TV Remote v2 (TV remote, keyboard, foreground app)

- Pairing on TLS 6467, remote on TLS 6466. The client presents a self-signed RSA 2048 certificate; the TV binds the pairing to it, so it is reused on every connection and replaced only by pairing again.
- Client name: the pairing request's `client_name` is always the certificate's CN (`ClientNames.of`, read by `AtvPairing`). Google TV keeps one pairing per client name / certificate subject, so a second client with the same name replaces the first: observed by Unfolded Circle (integration-androidtv#39, Chromecast) and open-tv-remote (#1, Sony A80J); not yet reproduced on the XR80. Every install paired as `tutti` until 2026-10-28, so pairing a second phone unpaired the first. New identities are `tutti (<Build.MODEL> <4 hex>)`; the suffix keeps two phones of the same model apart. The model is never logged. An identity stored before (`tutti`, key under `tutti.atv.client.v2`) keeps loading unchanged; pairing again replaces it. Pairing stages a fresh identity (new keystore alias, recorded in `files/secure/atv_client.alias`) and commits it only once the TV accepts the code, so a cancelled or failed pairing leaves the stored one working; it reuses the stored name when that is already per-install, so the TV replaces this phone's own previous pairing (`ClientIdentityFiles`, `ClientIdentityUpgradeTest`).
- Frames: protobuf varint length prefix + message (`Framing`, `FrameDecoder`, robust to split and merged reads).
- Pairing: Request → Ack, Option → Option, Configuration → Ack, the TV shows a 6-hex code, Secret → SecretAck. Secret = SHA-256(client modulus ‖ client exponent ‖ server modulus ‖ server exponent ‖ last two code bytes), numbers as unsigned big-endian bytes; the first hash byte must equal the first code byte (typos caught locally).
- Session: the TV sends configure / set-active / pings (~5 s) which the client answers; then key injects (short / long press), IME batch edits (`ime_counter`, `field_counter` from the TV), app links (`market://launch?id=<package>`, and `intent:` URIs for the apps screen). The TV reports `RemoteImeShowRequest` (focused field, text, label), `RemoteImeKeyInject.app_info.app_package` (foreground app), power and volume.
- Key codes are Android `KeyEvent` codes; `KeyMap` maps them and the hardware keyboard.

#### Voice (hold to talk to the TV's assistant)

Reverse-engineered by [tronikos/androidtvremote2](https://github.com/tronikos/androidtvremote2) ([`remote.py`](https://github.com/tronikos/androidtvremote2/blob/main/src/androidtvremote2/remote.py), [`remotemessage.proto`](https://github.com/tronikos/androidtvremote2/blob/main/src/androidtvremote2/remotemessage.proto), [`demo.py`](https://github.com/tronikos/androidtvremote2/blob/main/src/demo.py)); no official documentation exists. `VoiceSession` implements it from these facts (no code copied):

- Feature mask: bits `PING 1, KEY 2, IME 4, VOICE 8, POWER 32, VOLUME 64, APP_LINK 512`. androidtvremote2 answers the TV's `remote_configure` with its own mask ANDed with the TV's `code1`, and `remote_set_active` with its mask; voice is enabled only when bit 8 survives. Our fixed 622 already carries bit 8; tutti keeps the TV's `code1` (`RemoteState.tvFeatures`) and, when bit 8 is absent, does not try.
- Messages (field numbers from that proto): `RemoteVoiceBegin { int32 session_id = 1; string package_name = 2 }`, `RemoteVoicePayload { int32 session_id = 1; bytes samples = 2 }`, `RemoteVoiceEnd { int32 session_id = 1 }`, at `RemoteMessage` fields 30, 31, 32.
- Sequence: the client sends `KEYCODE_SEARCH` (84, not `KEYCODE_VOICE_ASSIST`); the TV answers `remote_voice_begin { session_id }` (the TV fills `package_name`); the client echoes `remote_voice_begin { session_id }` ("required by the protocol"); then payloads; then `remote_voice_end { session_id }`, with no reply awaited. androidtvremote2 gives the TV 2 s to answer.
- Audio: 16-bit PCM, 8 kHz, mono ("Default audio sample payload ... split into 20 KB messages"; the audio configuration in `RemoteVoiceBegin` is unknown). Payloads at most 20 480 bytes; a shorter piece is padded with zero bytes to 8 192. No pacing or acknowledgement: chunks go as they are captured (the demo's buffers are ~1 s). The demo caps a stream at 10 s; tutti caps at 15 s and closes the session itself.
- Community notes, single devices, unverified here: on a TCL TV 8 KiB messages were ignored and 20 KiB worked; the TV detects end of speech itself ([azylman/mirrormere#607](https://github.com/azylman/mirrormere/issues/607)); an older report says some TVs close the connection after payloads ([XDA](https://xdaforums.com/t/voice-input-in-android-tv-remote-control.4712015/)).
- Fallback when the TV does not offer voice: the search key alone opens the TV's own search screen, where the physical remote's mic or tutti's keyboard can take over; tutti says so.
- tutti's flow: the phone mic opens on press (before the TV answers; up to 15 s of audio is held meanwhile), full 20 KiB chunks stream as they fill, release sends the padded remainder and the end; sliding off, backgrounding or a mic error sends the end without the remainder. A begin that arrives after a cancel or a timeout is closed with an end. Phones whose mic refuses 8 kHz record 16 kHz and `VoicePcm.halve` averages pairs (crude low-pass, no plain decimation).

### 2. Soundbar IP control, TCP 33336

JSON objects `{"id","type":"get|set","feature","value"}` (requests newline-terminated; replies split by brace depth, never by newline, because the reference client sony-cisip2 notes the device "may send concatenated JSON objects with no delimiter") → `result` (feature + value for `get`, `"ACK"` for `set`) and unsolicited `notify`. No authentication; one persistent socket; requires "External control" in BRAVIA Connect. DRC and Auto Volume do not notify and are polled. The reducer shows a `set` at once, confirms on ACK (or the asked value echoed back) or a matching notify (whichever comes first), and rolls back on refusal, timeout (3 s) or disconnect. A `set` that times out is asked again with a `get`, and stays overdue for 15 s so a late ACK still confirms it; a value the bar reports clears its "didn't take" (Erwann's 360 Spatial tile showed On beside the warning, 2026-10-25). A `get` answered `ERR` or `NAK` is a refusal, never a value: the feature goes in `TheatreState.refused`, and the reducer test holds that.

Réglages › Réglages système de la barre is probe-gated row by row: a setting shows only once the bar has reported a value for it (`TheatreState.supports`, a `get` answer or a notify), so what the Bar 9 lacks stays hidden instead of greyed. `refreshAll` asks every feature at connect, paced (three `get`s in flight, 60 ms apart, 1.5 s each; the silent ones asked once more), and the poll re-asks what was neither answered nor refused every third round; the decoder accepts string ids, numeric or boolean values, `type` in any case, and an untyped message by its `id` (result) or feature (notify). The last 50 raw exchanges on the socket (`TheatreWireLog`, scrubbed) go into the diagnostic report as `live bar wire`, followed by one pinned `last set <feature>` line per feature tutti set this session (the request, the bar's reply or its silence, a notify that followed, with timings) that the ring never rolls past, and the report's own bar pass lists every feature as answered, refused or silent; the diagnostic report lists the refused keys, never values. tutti never asks for `system.serialnumber`, `network.macaddress` or `network.ipaddress`, and never touches `system.externalcontrol` (turning it off would cut tutti's own socket): `TheatreFeature.NEVER_ASKED`, tested.

### 3. BRAVIA REST, JSON-RPC + the code shown on the TV, or a PSK

`POST /sony/{system|audio|avContent|appControl|video|videoScreen}` with `X-Auth-PSK` (HTTP port 80, or HTTPS port 443 on EU models under RED-DA). Discovery runs first: `guide.getSupportedApiInfo` (`/sony/guide`, no auth, the documented call), falling back to `getMethodTypes` per service (not in Sony's reference); the settings UI shows only what the TV lists, and calls to unlisted methods fail fast. Picture (`get/setPictureQualitySettings`), sound output (`get/setSoundSettings`), speaker settings, inputs (`getCurrentExternalInputsStatus`, `setPlayContent`), apps (`getApplicationList`, `setActiveApp`), power and power saving, Wake-on-LAN mode (`get/setWolMode`), scene select (`videoScreen.get/setSceneSetting`), system information, volume information, IRCC (`/sony/ircc` SOAP, codes from `getRemoteControllerInfo`). When `setSoundSettings` is listed without `getSoundSettings`, the output is a write-only choice of the four documented `outputTerminal` values (`speaker`, `speaker_hdmi`, `hdmi`, `audioSystem`). A range is a lone candidate with max above min: Sony sends -1 for min, max and step on non-numeric targets. Réglages › TV opens whenever a TV is paired; while REST is not ONLINE it explains how to turn IP control on (distinct text for a refused PSK) instead of showing dead rows. EU units may serve HTTPS only: after authenticated success the transport pins SHA-256 of the server certificate's SubjectPublicKeyInfo (SPKI), not the whole self-signed certificate. A certificate reissue with the same key therefore keeps working; a new key fails closed until an explicit Remote v2 pairing refreshes REST trust. Legacy full-certificate pins remain readable and are promoted to SPKI after their next authenticated HTTPS success.

#### Authentication: the code shown on the TV first, the PSK second (Erwann, 2026-10-25)

IP control takes one of two credentials, one at a time (setting either removes the other):

- **The code shown on the TV**, Sony's "Normal" authentication, offered first and marked recommended (« Je suis friand des PIN affichés sur l'écran »): no key to invent in the TV's menus. `accessControl.actRegister` v1.0 (`/sony/accessControl`) with `[{clientid: "tutti:<uuid>", nickname: "tutti", level: "private"}, [{function: "WOL", value: "yes"}]]`. Sent without credentials it answers 401 and the TV shows a 4-digit code; sent again with `Authorization: Basic base64(":" + code)` it answers 200 with `Set-Cookie: auth=…`. Every later call carries `Cookie: auth=…` instead of `X-Auth-PSK` (`BraviaClient(transport, cookie = …) { psk }`; the cookie wins if both were ever present). The request shape is pybravia's (`client.py` `register`, used by Home Assistant) and python-bravia-tv's (`braviarc.py` `connect`); Sony's page could not be fetched when this was written. Unlike pybravia, which starts with the code "0000", tutti asks with no credentials, and a 403 there means the TV won't register at all (IP control off, or authentication set to the PSK alone). `IpRegistration` (pure, `IpRegistrationTest`) parses the cookie: `Max-Age` wins over `Expires`, `Expires` is read leniently because some TVs send a non-RFC date (pybravia strips it), a value with anything but cookie-octets is refused. The app stores `AuthCookie.encode()` (client id, obtained, expiry, value) under `ipcookie/<id>` in `secure.preferences_pb`, so the backup rules are unchanged; "Forget" removes it with the rest.
- **Renewal, unverified.** The cookie is commonly reported to last 14 days (`Max-Age=1209600`); tutti uses what the TV sends, else assumes a week. Three days before expiry (or a week in when unknown) the REST loop calls `actRegister` again with only the cookie and keeps a fresh `Set-Cookie`; a 200 without one keeps the old cookie and is not retried for 6 h. A 401 on a call, or on that renewal, marks the cookie "to renew" (`IpCodeStatus.RENEW`): the TV row reads « Contrôle IP : code à renouveler » with « Renouveler le code », which goes straight to a new code. pybravia and Home Assistant renew differently, by keeping the code and registering with it again; tutti keeps no code. Whether the TV renews on the cookie alone, and whether it shows a code with its screen off (Sony's 40005 "Display Is Turned off" says not), are **unverified**.
- **The PSK**, as before (`X-Auth-PSK`), now « Utiliser plutôt une clé PSK » inside the same dialog.

On the TV, either way: IP control on, Authentication "Normal" (code) or "Normal and Pre-Shared Key" (both). Settings › Network & Internet › Home network › IP control › Authentication is the path in Sony's guide; the consumer menu labels on the XR80 are unverified.

### 4. Sony-cloud gRPC (opt-in "Connexion Sony (expérimental)")

Bar on h2c port 55051, TV on a port advertised by mDNS `_sonysmarthome._tcp`; Sony Seeds OAuth (PKCE, Custom Tab), ~24 h session keys, HMAC-signed handshake, `GetStatesWithAuth`, `ExecCommandWithAuth`, `StartNotifyStates` over dotted field paths. The request envelope (`serialized_request + hmac`), the HMAC input and the Seeds OAuth endpoints are not documented precisely enough to implement without guessing, so `:protocol` stops at `SonyCloudPlane` and `:app` binds `UnavailableSonyCloudPlane` ("non disponible"). Failures there never touch TCP/REST.

**Not pursued (Erwann, 2026-10-28).** What it would add (the bar's Bluetooth device and codec, a few bar settings missing from TCP) does not justify guessing Sony's signing scheme and handling a Sony sign-in. The interface stays as it is; nothing more gets built on this plane unless a specific feature calls for it.

### 5. Out of reach

Acoustic Center Sync, sound calibration, speaker placement and first setup: a shortcut opens the TV's sound settings (v2/IRCC keys), and "Recalibrer dans BRAVIA Connect" deep-links to Sony's app.

### 6. Bluetooth HID: the phone as the TV's keyboard and mouse (optional, no LAN)

Erwann, 2026-10-25: "clavier, souris, trackpad en mode Bluetooth si besoin", then "un mode pointeur sur l'écran". First built as Settings › Bluetooth › Bluetooth keyboard and mouse, a screen of its own; since revision 4 the remote itself, with only pairing in Settings. The phone pairs straight to the TV as a Bluetooth keyboard + mouse through Android's `BluetoothHidDevice` profile (API 28; tutti's minSdk is 29). Useful when the LAN link is down, and for what Remote v2 can't do: a real cursor, a physical keyboard's keys.

**ADR (Maya, 2026-10-25).**
- *Context.* Android lets **one app at a time** register as a HID device; Erwann already uses a third-party "Bluetooth Keyboard & Mouse" app and will compare. HID sends key *positions*, so text depends on the layout the TV has chosen for the keyboard. The open question of background sessions (tutti keeps no foreground service anywhere) applies here too. No new dependencies.
- *Options.* (a) Register at app start and keep the role while tutti runs, with a foreground service to survive the background: always ready, but it squats the profile, breaks the other app, and adds a persistent notification and a battery cost for a fallback mode. (b) Register only while the Bluetooth screen is in front, unregister on leave: costs a reconnect (a second or two, unverified) each time the screen opens. (c) Route typing over Remote v2 when the LAN is up and HID only for the cursor: better accents, but one screen would then use two links with different failure modes (Iris: keep which link a gesture uses unambiguous).
- *Decision.* (b). `HidLink` (`:app`, `platform/bluetooth/`) registers on the screen's ON_START, unregisters and closes the proxy on ON_STOP and on leaving; no foreground service, no background hold. It remembers the last connected TV's Bluetooth address (non-secret prefs, `bluetooth_hid`) and calls `connect()` once registered. A registration Android refuses (`registerApp` false, or `onAppStatusChanged(registered = false)` while we want it) reads "another app is using the phone as a Bluetooth keyboard". Report bytes, key mapping and pointer maths are in `:protocol/hid`, pure and tested; `:app` only registers, connects and sends.
- *Consequences.* Never fights another HID app in the background; the cost is a reconnect each visit and nothing over Bluetooth while the screen is closed. If on-device use shows the reconnect is too slow, the next step is an explicit "keep Bluetooth on" switch (still no background grab without it), not a silent service.

**Revision (Maya, 2026-10-25, after Erwann: « la même interface, qu'importe si c'est Bluetooth ou Google TV »; then « contrôler mon macOS quand je le display sur la TV »).**
- *Context.* Erwann wants one remote, not a second Bluetooth app: the link is an implementation detail. And a second Bluetooth host, the Mac shown on the TV (HDMI or AirPlay), with the phone as its trackpad, gyro pointer and keyboard. Exactly two targets, TV and Mac; nothing general-purpose.
- *Decision.* Keep (b)'s rule that the HID role is never held in the background, but move *when* it is held: while the remote is in front and `HidRoute.hidHost` names a host. Both targets stay live at once (Erwann: « autant se connecter à la TV qu'au Mac, et pouvoir switcher »): the TV on its LAN links, the Mac on the one HID connection, opened as soon as the remote is in front and the Mac is configured, whatever the target, so a switch is only routing and the first Mac key never waits on a connect. The connection moves from the Mac to the TV only when the TV is the target and its LAN is down, and the remote says so in words. Released when tutti leaves the foreground. Each control picks its link with `HidRoute.link` (TV: LAN first, Bluetooth fallback; Mac: Bluetooth only) and maps through `HidRoute.action` (D-pad to arrows, OK to Enter, Back/Home/media/volume to consumer usages on the TV, Back to Esc on the Mac, no Home or volume for the Mac: its sound goes out over HDMI to the bar). Each target remembers its own Bluetooth address and layout (`Device.layout()` never lets a TV layout type to a computer, nor a Mac layout to a PC). A HID device has one host connection at a time, so switching target disconnects the other first; that Android's `BluetoothHidDevice` holds one connected host is from its docs, **unverified** on Erwann's Pixel.
- *Consequences.* The Settings screen shrinks to setup. Not yet built (next step, `:app`): `HidLink` holding two remembered addresses and the target, the remote's controller routing keys through `HidRoute`, the target switch, the card's « Contrôler le Mac », the scroll strip and three buttons, the gyro pad mode. The `:protocol` half (layouts, routing, link choice) is built and tested.

**Revision 2: a device list (Maya, 2026-10-25, Erwann: « ok lance l'étape 1 avec le mode Mac »).** Supersedes "exactly two targets" above.
- *Context.* Erwann may have more than one Mac on the TV, and wants Settings › Devices to be a list. Stage 1 of the devices proposal: one TV, one bar, any number of Macs, without touching the TV and bar engine. Scope stays the living room's remote (CLAUDE.md): no generic HTTP or Bluetooth device.
- *Model* (`:protocol devices/`, pure, tested). `Device(id, name, kind, links, shownOn)`: `DeviceKind` TV, SOUNDBAR, MAC (COMPUTER since revision 3) decides behaviour (`kind.hidTarget` gives `HidRoute` its personality; the bar has none); `DeviceLink` Google (Remote v2), SonyIp ("HTTP": REST + PSK, and only that), BarIp (TCP 33336), Bluetooth (address + layout name); `ShownOn(hdmiInput, airplay)` for a Mac. `DeviceKinds.allowedLinks` refuses nonsense (a bar on Bluetooth, a Mac on Google). Decoding is lenient per item: a link or kind from a newer build is skipped, never the whole list.
- *Storage and migration.* Non-secret list in `tutti.preferences_pb` under `devices_v2`; until written, it reads as `DeviceMigration.migrate` of the version-1 `devices` key plus the Bluetooth screen's remembered host, meant to be the TV, so it becomes the TV's Bluetooth link; revision 4 drops it when it is a computer. `migrateDevices()` writes it once; every write also rewrites `devices` from the list for one release, so a downgrade keeps its TV and bar. The rest of the app still reads `Devices(tv, bar)` as a view (`DeviceViews`), and writes through it touch only the TV's and bar's LAN links. Secrets per device in the same `secure.preferences_pb` (`psk/<id>`, `pin/<id>/remote`, `pin/<id>/rest`), so the backup rules do not change. `SecretMigration` **copies** the encrypted blobs (the cipher binds nothing to the key name, so nothing is decrypted), never moves them; reads fall back to the old keys, writes go to both for one release, "Forget" removes both. Tested on a real DataStore file. The old keys go in a later release.
- *Target.* `Targeting.auto`: the Mac whose `hdmiInput` is the TV's current input (needs the PSK: `getPlayingContentInfo`), else the TV. A manual choice (`TargetChoice`) holds until the input changes. `Targeting.route(key, target, tvLanUp, hidConnected)` gives every key its link and an availability with one reason (`NOT_ON_MAC`, `NOT_OVER_BLUETOOTH`, `LINK_DOWN`); Home, Apps, Settings, inputs, Power and volume keep their TV meaning over the LAN whatever the target. Text from the phone field becomes erase-to-common-prefix plus keystrokes in the target's layout (`Targeting.textEdit`). AirPlay: no auto-switch yet; `TargetController.foregroundLog` keeps the TV's last ten distinct foreground packages so one mirror shows Sony's receiver.
- *HID.* `HidLink` registers while any holder wants it (`acquire`/`release`: the remote, Settings › Devices and the TV's pairing step) and `hold(address)` points the one connection at a device, disconnecting the current host first. `TargetController` holds it only while tutti is in the foreground (MainActivity onStart/onStop) **and** the remote is in front (`remoteShown`), at `Targeting.hidHost`: the targeted Mac; the TV when targeted with its LAN down; otherwise the last Mac used stays ready. Never in the background.
- *Consequences.* `TargetController` is separate from `TuttiController` (2226 lines) on purpose. Presence (Bonjour, input `connection`) is stage 2: `TargetState.present` is every configured target for now. **Unverified on device:** a host switch on the Pixel, macOS accepting the phone as keyboard and mouse, reconnect time.

**Revision 3: any computer (Maya, 2026-10-25, Erwann: « c'est pas qu'un Mac, ça peut être n'importe quel type d'ordi »).** `DeviceKind.MAC` became `COMPUTER`, with `Device.os` a `ComputerOs` (MACOS, WINDOWS, LINUX; ChromeOS left out: its French layout and pairing words would be guesses). `HidTarget.COMPUTER` is the one Bluetooth personality for all three, so routing is unchanged (Back to Esc, D-pad to arrows, OK to Enter, media keys; no Home or volume; `NOT_ON_COMPUTER` for keys with no meaning). The system only picks the layouts, `Device.layouts()`, default first: macOS `MAC_FR`, `MAC_US`; Windows and Linux the PC tables `FR_AZERTY` (AltGr third level), `US`; the TV keeps `US`, `FR_AZERTY`. A stored layout from another system falls back to the default. AirPlay (`Device.airplay`, `ShownOn.airplay`) is a Mac's only. Migration: `@JsonNames("MAC")` reads what v0.2.0-dev.1/2 stored as `COMPUTER`, and `DeviceListSerializer` gives a computer without `os` macOS, so the next write stores `"kind":"COMPUTER","os":"MACOS"`; the stored literal JSON is tested in `DevicesTest` and, on a real DataStore file, `UpgradeFromDev2Test`. A downgrade to dev.2 drops the computers (lenient decoding skips the unknown kind) and keeps the TV and the bar. The add flow's input polling uses `TuttiController.refreshInputs()` (one `getCurrentExternalInputsStatus`, only `connected` changes) instead of the whole `loadTvSettings` sweep.

**Revision 4: the screen goes, the TV's link is checked (Maya and Iris, 2026-10-25, Erwann: « Je croyais qu'on gardait ceux de l'écran main »).** `BluetoothScreen` and its `bluetooth` stack key are removed; the remote already carried all of it. The screen also showed a computer under the TV (« Connecting to <computer>… »): `HidLink` remembered the *last host connected* (`bluetooth_hid`/`host`) whatever it was, reconnected it on every registration with no host asked for (also Android's `pluggedDevice`), and that screen offered every bonded device, computers included, so the name was a bonded computer's Bluetooth name, and the same address could become the TV's link at the version-1 migration. Now `HidLink` connects only to the host it is told to `hold` and remembers nothing; a host may still connect from its side (pairing). `DeviceMigration.withoutStrayTvBluetooth` (tested) drops a TV Bluetooth link equal to a configured computer's or a bonded host whose class is computer; `TargetController` applies it whenever the list or the bonded hosts change. The TV's link is now set only by the TV row's pairing step (`tvPairingShown`, `linkTvBluetooth`, which refuses a computer) and cleared by its « Oublier » (`forgetTvBluetooth`). The old `host` pref is still read by the version-1 migration, never written.

**Mac layouts.** `KeyLayout.MAC_FR` (Apple "French" AZERTY, the Mac's default here) and `MAC_US`: Option is HID Alt, Command is HID GUI. Apple French: @ # left of 1 (usage 0x35), & é " ' ( § è ! ç à on the number row, ) ° and - _ after it, { [ on ⌥/⌥⇧ ( and } ] on ⌥/⌥⇧ ), | on ⌥⇧L, \\ on ⌥⇧:, € on ⌥$, « » on ⌥7, œ on ⌥o, ~ ñ ã õ through the dead ⌥n, ^ ¨ as on the PC layout. US Mac types every accented letter through macOS's dead keys (⌥e ⌥` ⌥i ⌥u ⌥n), capitals included, plus ç œ æ ß « » € £. Not typable: ` on Apple French (a dead key by Return whose usage is unverified) and accented capitals there. **Unverified on the Mac:** macOS's Keyboard Setup Assistant classifies an unknown keyboard as ANSI, ISO or JIS and on ISO may swap 0x35 and 0x64 (@ and <); if Erwann sees them swapped, the fix is those two lines.

**Descriptor** (`HidDescriptor`, tested by walking its items): one composite device, SDP subclass 0xC0 (combo). Report 1 keyboard (boot layout, 8 bytes: modifiers, reserved, six usages, roll-over past six), report 2 mouse (3 buttons, relative X, Y, wheel as int8, 4 bytes), report 3 consumer control (one 16-bit usage: Home 0x223 and Back 0x224 as AC Home/AC Back, play/pause, next, previous, mute, volume up/down; Android's `Generic.kl` maps these). No LED output report.

**Permissions.** `BLUETOOTH_CONNECT` (register, connect, send, read bonded names) and `BLUETOOTH_ADVERTISE` (the "make visible" request) on API 31+, asked in Settings only (the TV's pairing step, the add-a-computer flow); `BLUETOOTH`/`BLUETOOTH_ADMIN` capped at API 30. No `BLUETOOTH_SCAN`: the TV scans, the phone is found. Bluetooth and gyroscope are `required="false"` features.

**Pairing.** On the TV: Settings › Remotes & Accessories › Pair accessory (Google TV wording, the XR80's exact menu **unverified**). On the phone, with the TV row's « Bluetooth de secours » step open (so tutti is registered and advertises a keyboard/mouse class), "Make visible" asks Android for 120 s of discoverability; the TV lists the phone, both show a code, Android's own dialog confirms. Bonding is Android's: « Oublier » removes the TV's Bluetooth link from tutti and disconnects; removing the bond itself has no public API, so it stays in Android's Bluetooth settings.

**Support.** `HidLink.probe()` asks for the profile proxy and lets it go: a ROM that disables the HID device role returns false or never answers (3 s), and the TV row then hides « Bluetooth de secours » (the add flow says why a computer can't be added). Registration can still be refused later (another app), which the screen states with a retry.

**Typing.** `KeyLayout` maps characters to positions for the layout the user says the TV uses (QWERTY US by default, which is what Android assumes for an unknown keyboard; or AZERTY French). On AZERTY: é è ç à ù are on their own keys; â ê î ô û and ä ë ï ö ü ÿ go through the dead ^ / ¨ key then the letter; € @ # { } [ ] | \ via AltGr. **Not typable** on either: É È À Ç Ù as capitals, œ æ, « », and on AZERTY ~ and ` (dead keys on AltGr). They are not sent and the remote names them. On QWERTY US no accent can be typed at all. Remote v2's keyboard (the LAN one) sends text, so it types anything; that stays the better path for accents when the LAN is up.

**Touchpad and pointer.** Touchpad: finger pixels with a mild acceleration (`TouchpadMotion`), tap = left click, two-finger drag = wheel (one detent per 48 px, natural direction), two-finger tap = right click (Android: Back). Pointer (`AirPointer`, LG Magic Remote style): `TYPE_GYROSCOPE` at `SENSOR_DELAY_GAME`, rotation about the screen's normal moves the cursor sideways, about x up and down; a 0.03 rad/s dead zone (subtracted, so motion starts from zero), an EMA (0.45), 3200 cursor units per radian at sensitivity 1 (0.25 to 3), fractions carried between reports (`MotionAccumulator`), int8 splitting. "Hold to recentre" is the clutch: nothing moves while held, the filter restarts from rest on release. The sensor listener exists only while the pad's gyro mode is in front on a connected Bluetooth target.

### 7. Google Cast v2: read-only "now playing" (decided, Maya, 2026-10-25)

**Why.** Remote v2 tells the foreground package and REST tells inputs and broadcast. Neither one gives the title in an app. Cast v2 (TLS, TCP 8009) does that for apps built with Cast Connect. Erwann's BRAVIA 8 reported the title, the channel, the position and duration, and the play state for YouTube started from the TV (`catt status`, 2026-10-25). Netflix is known not to report (Home Assistant hard-codes it). A Cast reply is the only source. When there isn't one, the UI shows nothing new.

**Wire.** A 4-byte big-endian length and a protobuf `CastMessage` (`protocol/src/main/proto/cast/cast_channel.proto`, copied from chromium/openscreen at `2a78d154`, BSD licence beside it), at most 64 KiB per frame. Session (`CastSession`): device auth first (below). Then `CONNECT` and `GET_STATUS` to `receiver-0`. From `RECEIVER_STATUS`, the first application that lists `urn:x-cast:com.google.cast.media` gets a `CONNECT` and a media `GET_STATUS` on its `transportId`. `MEDIA_STATUS` from that transport is folded by `CastStatusReducer`, which keeps the title and duration when a later status leaves out `media`. We send a `PING` every 5 s and answer the TV's pings with `PONG`, and the media status is re-read every 15 s. The position runs on locally between reports while playing, for at most 40 s past the last reading (`CastNowPlaying.MAX_RUN_MS`), and never to the end while playing: a playing reading at or past its duration, a paused one past it, or a stale one shows no time at all, because the old clamp turned each of those into a confident "43:09 / 43:09" (2026-10-26). The diagnostic lists the last eight media statuses as raw numbers only (`CastReadings`: age, gap since the one before, playerState, currentTime, duration, playbackRate, answer or unasked, same or new mediaSessionId), never a title. Nothing is shown when the status is idle, has no title, or the app closes. tutti never sends a media command, because the Remote v2 keys already handle transport.

**Trust model (the ruling).** A Cast device's TLS certificate is self-signed and lives at most 4 days (Chromium's `kMaxSelfSignedCertLifetimeInDays`), so the trust-on-first-use pin used everywhere else would break within days, and trust-all is ruled out. tutti authenticates the device the way Chromium and Open Screen do (`cast_auth_util.cc`, `cast_cert_validator.cc`):

1. The TLS handshake records the peer certificate and makes no trust decision of its own. Until step 3 passes, the connection carries nothing but our challenge, and nothing it receives is read.
2. We send `urn:x-cast:com.google.cast.tp.deviceauth`, an `AuthChallenge` with a fresh 16-byte random nonce, asking for SHA-256 and PKCS#1 v1.5.
3. `CastDeviceAuth.verify` checks five things:
   - the peer certificate is inside its validity dates and expires no more than 4 days from now;
   - the signed nonce is ours;
   - the device certificate chains through the reply's intermediates to a **bundled Google Cast root**, with every signature, every validity window and the CA flag on each issuer checked, at most 5 deep, and `digitalSignature` set on the leaf when it has a key usage;
   - the signature algorithm is RSASSA-PKCS1 v1.5, with SHA-1 accepted for older devices as Chromium does;
   - the signature over *nonce ‖ DER of the TLS certificate presented in this handshake* verifies with the device key.

   A man in the middle presents a TLS certificate of its own, so it can neither reuse a real device's signature nor make one.

The anchors are `CastRoots`: Google's public "Cast Root CA" (SHA-256 `80:9A:F1:47:…:D6:CA`, until 2034) and "Eureka Root CA" (`CA:F6:D1:E3:…:BC:46`, until 2032). They are copied from openscreen's `cast_root_ca_cert_der-inc.h` and `eureka_root_ca_der-inc.h`, the anchors Chromium trusts, and `CastDeviceAuthTest` pins their fingerprints. The chain walk is written out by hand rather than handed to PKIX, so the JVM tests and Android's provider apply the same rules. CRLs are not checked; Chromium treats them as optional too. The root trusted for CRLs is not bundled.

**Fallback.** Any failure means nothing is shown and the socket is closed: auth (`CastAuthFailure`: malformed, device error, peer dates, nonce, algorithm, untrusted chain, bad signature), a malformed frame, a closed socket, or a host that isn't private. The reason is logged as a class only (`CastEnd`), never a value from the device. The card falls back to what Remote v2 and REST already say. We don't retry in a tight loop.

**Scope.** We connect only to the configured TV's host, only when it is a private address (`LanAddress.isPrivate`), only on port 8009, and with no client certificate. No mDNS is needed, because the host is already known. The session runs only while the remote screen is in front, and it closes when the screen leaves or the TV's host changes. Titles and artists are personal viewing data. `CastNowPlaying.toString` redacts them, they are never logged, never stored, and never put in the diagnostic. **Artwork (Erwann, 2026-10-28, the one exception to "images only from the TV")**: `metadata.images[].url` is kept only when `CastArtwork.isAllowed` passes: HTTPS, port 443, no user info, host exactly `i.ytimg.com` (YouTube thumbnails) or `lh3.googleusercontent.com` (YouTube Music's art; from client libraries, not yet seen from the XR80), at most 2,048 characters; the first such URL wins and the rest of the list is ignored. `CastArtworkLoader` (`:app`) fetches it with its own OkHttp client: system trust store, no redirects, no cookie jar, no HTTP cache, no auth header, only a 200 with an `image/*` type and at most 512 KiB read, at most 4096 px a side, decoded down to the tile's width. Bitmaps live in a six-entry memory LRU keyed by URL; a failed URL is not asked again until the process restarts. The URL carries the video id, so it is viewing data like the title: redacted in `toString`, never logged, never on disk. No setting turns it off (Maya): the request goes from the same home network, about the same item, to the company whose app is playing it on the TV, and carries nothing else of ours; an off switch would guard nothing. Revisit if a host joins that the playing app does not own.

**State.** `:protocol` (framing, auth, parsing, reduction, session) is built and tested on invented data, with a test PKI generated per run. `:app` (2026-10-25): `AndroidCastConnector` (private host first, port 8009, no client certificate, 20 s read timeout) with `PeerRecorder`, a trust manager that refuses an empty chain or an out-of-date leaf and otherwise only records the leaf for `CastDeviceAuth`. `CastWatcher` runs one session while the remote is in front, the TV is on and its host is configured, closes it on leaving or a new host, and backs off per host (`CastBackoff`: 5 s doubling to 5 min, 30 min after an untrusted device, reset by a session that lasted a minute), a wait that outlives leaving the screen (`CastWatcherTest`, fake connector). `TuttiController.castNowPlaying` feeds the full card's Cast line, the playback sheet's header and the one media session in `QuickNotifications` (title, artist or channel, duration, position, speed, playing or paused); with no report the session keeps its usual fields and `STATE_PLAYING`. A paused state there costs the volume keys nothing, because Cast only runs while the remote is in front, where the activity takes them. No seek or transport action reaches Cast; the session's buttons stay on the Remote v2 keys. **Unverified on the XR80:** that its Cast receiver answers deviceauth with a chain to one of these two roots (Chromium relies on this for every Cast device, Sony's built-in receiver included, but tutti hasn't seen it), and how `RECEIVER_STATUS` names a non-Cast-Connect app in front.

## Gentle switch-off timer (decided, Maya, 2026-10-25; built in `:app` `sleep/`)

Iris's top 10, item 5: "turn off in 15/30/45/60/90 min", the bar's volume stepping down over the last two minutes, then the TV and the bar off. The timing is pure and tested in `:protocol` (`sleep/SleepFade.kt`): phases, the stepped level, "a hand on the rail wins" (the fade only ever lowers), the next wake-up, and the level to restore on a cancel mid-fade.

The phone side, chosen with Android 14+ in mind:

- **A `connectedDevice` foreground service for the whole timer**, started from the Power sheet while tutti is in front (always allowed). Its notification is the timer: "Off at 23:40", a countdown chronometer (`setUsesChronometer` + `setChronometerCountDown`, so nothing redraws it) and Cancel. The type fits Play's definition (it drives LAN devices) and needs `FOREGROUND_SERVICE_CONNECTED_DEVICE` plus one prerequisite permission, which `CHANGE_WIFI_MULTICAST_STATE` already is. It holds **no wake lock while waiting**: an idle service costs next to nothing.
- **An exact alarm wakes it at the fade's start** (`setExactAndAllowWhileIdle`, which fires through Doze), guarded by `canScheduleExactAlarms()`. tutti asks for `SCHEDULE_EXACT_ALARM`, the user-granted one; never `USE_EXACT_ALARM`, which Play reserves for alarm and calendar apps. On Android 14+ that permission is off by default for new installs, so the sheet offers the system page that grants it.
- **The fade itself runs under a partial wake lock** capped at 3 minutes: twelve steps ten seconds apart, then Power off for both, then the service stops. Every step is LAN-only, through the controller's existing sockets.
- **Without exact alarms**, tutti falls back to `setAndAllowWhileIdle`, which Doze may defer by several minutes, and the sheet says so in words ("may switch off a few minutes late"). If the process was killed and the alarm restarts it, the service starts from the alarm (an exact alarm exempts it from the background-start ban); after a reboot the timer is gone and the notification with it, which is honest.
- **The TV's own sleep timer is not the backstop**: Sony documents no setter, only an IRCC key that cycles steps the TV shows on screen, so tutti can't set a known duration through it.
- **Unverified**: the fade and off on a real phone in Doze, the bar's response to a step every ten seconds, and the phone keeping Wi-Fi through Doze (an app with a foreground service keeps network access).

## Rulings for builds in flight (Maya, 2026-10-25)

**Cast stays read-only: no SEEK.** The scrub strip (benchmark idea 2) moves by repeated Remote v2 fast-forward and rewind keys, and Cast only *shows* where that lands. A Cast `SEEK` would be tutti's first command into a media session another sender launched: it turns a channel whose whole threat analysis is "nothing secret, nothing written" (§ 7) into a control plane, on a device auth not yet seen working on the XR80, for an app set (Cast Connect apps) that the keys already drive. Revisit only when both hold: deviceauth has passed on the XR80, and the strip measurably misses its target with keys. Then the one command allowed is `SEEK` with an absolute `currentTime`, on the `mediaSessionId` of a `MEDIA_STATUS` read in the last 15 s, after the same auth; never `LOAD`, `STOP`, `SET_VOLUME` or a queue command, and never on a session whose status we haven't read.

**Scenes from outside the app (benchmark idea 10).** A scene can switch the TV off or set the volume, so any app able to fire one is a remote of the living room. Rules: (1) one exported entry point only, a dedicated no-UI activity or receiver, guarded by a custom permission `io.kud.tutti.permission.RUN_SCENE` with `protectionLevel="dangerous"`, so Tasker gets it only when Erwann grants it in system settings; `signature` would shut Tasker out, `normal` protects nothing. (2) Off by default: a setting "Let other apps run scenes", and with it off the entry point does nothing. (3) An allow-list: each scene carries its own "runnable from outside" mark, default off; the intent carries only a scene id, an unknown or unmarked id does nothing and is logged as a class, never echoed. (4) No `BROWSABLE` category and no web deep link, ever. (5) NFC goes through the same allow-list and opt-in: a tag holds `tutti://scene/<id>` plus tutti's Android Application Record, since any visitor can rewrite a tag. (6) At most one outside run every 2 s. Found while ruling: `MainActivity` is exported (it is the launcher activity) and applies `ACTION_SCENE` with any scene id from any caller today; closed (2026-10-26): launcher scene shortcuts carry a per-install random token (`ShortcutGuard`, 32 bytes, kept encrypted in the secure store under `shortcut/token`, never logged, untouched by forgetting a device), and `handleShortcut` runs an `ACTION_SCENE` only with that exact token; anything else just opens the app. At every start the dynamic shortcuts and every pinned scene shortcut whose scene still exists are republished with the token, so an old pinned shortcut works again once the updated app has been opened; tapped before that first opening, it opens the app without running its scene.

## Finding a device again after its address changed (Maya's top 10, item 4)

After three connection failures in a row at the stored address (`Rediscovery.AFTER_FAILURES`, the 1, 2 and 4 s backoffs), the session browses mDNS once, at most every ten minutes per device (`Rediscovery.due`), and probes each new private address it finds (`Rediscovery.candidates`: never the stored address, never the other device's). Pure rules in `:protocol` `net/Rediscovery.kt` and `theatre/BarProbe.kt`, tested.

- **The TV moves only on proof.** `_androidtvremote2._tcp`, then for each candidate a Remote v2 TLS handshake with the stored pin (the connector refuses any other certificate; nothing is sent after it), or, when that fails and the REST pin is a public-key pin, one unauthenticated `getInterfaceInformation` over HTTPS pinned to that key. Only an exact match of the pinned certificate or key (`Rediscovery.tvConfirmed`) rewrites the stored host; every session then restarts there, pins, MAC and pairing untouched. A legacy full-certificate REST pin is left to the Remote v2 pin. No pin, no move.
- **The bar is only ever an offer.** Port 33336 has no authentication, so nothing proves which bar answers. tutti browses `_googlecast._tcp`, `_airplay._tcp` and `_spotify-connect._tcp`, asks each new address one `get system.modeltype` (`BarProbe`, read-only, its own connection, closed at once), and keeps the first that names a model, the same model as the configured bar when it is known (`Rediscovery.barOffer`). Connexions then reads « semble répondre à une nouvelle adresse » with « L’utiliser »; only that tap changes the stored host. The offer goes when the bar answers at its own address again.
- **Unverified on real hardware:** which of those three services the Bar 9 advertises, and that the XR80 keeps advertising `_androidtvremote2._tcp` at its new address.

## Diagnostic (Réglages › Diagnostic)

`:protocol`'s `DiagnosticRunner` walks every plane against the configured devices with its own read-only connections: mDNS discovery; REST `getInterfaceInformation` (no PSK), `getSystemInformation` (PSK), `getMethodTypes`, then only the getters the TV lists (since item 9: `getCurrentTime`, `getWolMode`, `getSceneSetting`, and `getSettingsSchema` under whichever service lists it, never guessed); the v2 remote's TLS connect and handshake (it answers configure, set-active and ping, and sends nothing else); the pairing port's TCP reachability; a `get` for every soundbar feature, Voice Zoom 3 included. Each step records ok / failed / skipped, its time, a short error class and what the device reported. `DiagnosticReport` renders the plain-text report, scrubbed through `Redact.text` with the hosts, PSK, pin and every identifying value seen in a reply (`JsonShape` keeps keys and types, values only for harmless keys). Pins seen during a run are never saved. A text field the TV opens (live, or during the run) shows as its `int5` and the kind that number gives when read as an Android input type (`ImeFieldKind`, e.g. 129 → text/password), marked inferred; never its text, and the label only by length. That reading is groundwork for masking password fields (item 10), which waits on a report from the XR80. The environment also gives each link's time to ready this session, last, best and worst (`LinkTimings`, item 8): Remote v2 from the connect to its configure exchange, IP control to its discovery answer, the bar to its open socket, Cast from the connect to its first status read after device auth. The Sony-cloud step stays a skip: `SonyCloudPlane` has no read-only call to make (no `GetCapabilities`, no h2c transport), so the gRPC probe waits for that transport (bravia-connect.md, phase 2 step 3).

## Release build: R8

Release builds are shrunk and optimised by R8 with `isShrinkResources` (Maya, 2026-10-25), and **keep their names** (`-dontobfuscate`, line numbers kept): the in-app crash log and the diagnostic report are the only stack traces a phone gives without adb, and they are pasted into bug reports as they are. Obfuscation would save a little more and make every report need `mapping.txt`. The unsigned release APK went from 36.9 MB to about 6.4 MB, mostly dex (33.9 MB to 5.0 MB, 193k to 26k method references).

Keep rules (`app/proguard-rules.pro`) cover what is reached by name:

- Glance builds an `ActionCallback` by class name, and a placed widget keeps that name in its PendingIntents until redrawn: every implementation keeps its name and no-arg constructor.
- Wire's generated protos are kept whole (small; `ProtoAdapter.get` and enum lookups reflect on them).
- kotlinx.serialization, Hilt, OkHttp, coroutines, DataStore and Compose bring their own rules. Every stored model is read through an explicit `serializer()`, and a JSON key is a string constant in its generated serializer, so shrinking cannot rename a stored field. Checked on the first R8 build: every stored property name, sealed `@SerialName` and enum constant of `platform/data/Models.kt` and `protocol/scenes` is in the release dex, and every stored root's `$serializer` is in `mapping.txt`.
- BouncyCastle is only reached through `ClientCertificates` (RSA self-signing via the platform JCA provider); its Picnic tables are excluded from the APK.

The Compose group-mapping file is off (`includeComposeMappingFile`): it only decodes obfuscated Compose traces. Not provable offline, so to check on a phone with each first R8 release: first launch over an existing install (stored devices, prefs, dock and scenes intact), pairing a TV (certificate generation), the widget's buttons, the tile and the notification actions.

## In-app updates (Maya, 2026-10-27)

Erwann installs a `-dev` pre-release about every hour, so About › Version checks GitHub itself (`platform/update/Updater.kt`; the rules, with tests, in `:protocol` `update/`).

- **Will it install?** Yes: every CI debug build is signed with the committed `app/debug.keystore` (since 2026-10-22), so each `-dev` APK installs over the last; a release build updates only from the release key. A debug build looks only for `*-debug.apk` assets, a release build only for the other `.apk`, so the updater never offers an APK Android would refuse for its signature.
- **When:** on a tap in About, and when the app opens or comes back to the foreground (`LifecycleStartEffect`), at most once an hour for a dev build and once a day for a final release (`CheckSchedule.intervalFor`); the newest build found and the one set aside with "Later" are kept in the `updates` preferences so the cue outlives the process (docs/design.md, "Updates"). Never in the background otherwise, never an install without Android's own confirmation (`USER_ACTION_REQUIRED`).
- **Where:** `GET https://api.github.com/repos/kud/tutti/releases` (pre-releases included, no token: 60 unauthenticated requests an hour is far more than once an hour plus taps). The asset's `browser_download_url` must sit under `github.com/kud/tutti/releases/download/`; redirects are followed by hand, each hop HTTPS on port 443 to `github.com`, `objects.githubusercontent.com` or `release-assets.githubusercontent.com` (GitHub's current asset host), at most five. Normal system trust, no pin, no cleartext: these are public hosts with public certificates, not LAN devices.
- **What is checked before installing:** the SHA-256 of the bytes against the `digest` GitHub reports for the asset (no digest, no offer), then that the APK's package name is this app's and its versionCode is higher. The file lives in `cache/updates/` and is deleted on any mismatch; PackageInstaller then checks the signature.
- **Versions:** `MAJOR.MINOR.PATCH[-dev.N]`, a dev build below its final release (0.2.0-dev.25 < 0.2.0-dev.26 < 0.2.0), the same order as android.yml's versionCode. A local build (`0.0.0-dev`) counts as dev 0.
- Permission: `REQUEST_INSTALL_PACKAGES`. Without the "install unknown apps" grant the sheet says so in words and opens Android's page for it, then carries on when the person comes back.

## Threat model

Assets: the TV PSK, the IP-control cookie, the Bluetooth HID role (keyboard and mouse input to the TV), the TV pairing (client private key + TV pin), Sony OAuth tokens and session keys (opt-in), and control of the living-room devices.

| Threat | Mitigation |
| --- | --- |
| Someone on the LAN impersonates the TV to capture the PSK or a pairing | Remote v2 pins the exact TV certificate established by its six-character pairing. BRAVIA REST pins the HTTPS public key (SPKI) after authenticated success; a reissued certificate with that key is accepted, but a new key fails closed and reads as "pair again". A successful Remote v2 pairing is the only ceremony that may refresh REST trust. Pins protect connections *after* first trust: an attacker already in the middle at first contact or pairing can still be pinned instead of the TV, so pair on a network you trust. |
| The IP-control cookie is a bearer secret | Whoever holds it controls the TV over IP until it expires, like the PSK. It is stored only encrypted in `secure.preferences_pb` (`ipcookie/<id>`, excluded from backup), never logged (`AuthCookie.toString` and `HttpReply.toString` redact it, `failureDetail` and the diagnostic scrub it by value), and travels by exactly the PSK's rules below: HTTPS to the pinned TV, or HTTP only to a private address once an unauthenticated probe answered there; never on discovery, never to an icon over HTTP, never through a proxy or a redirect. The code typed in goes by the same rules, once. It is scoped by the TV to this client id ("tutti" in the TV's list of remote devices), and the TV, not tutti, decides how long it lives. |
| LAN eavesdropping on REST over HTTP | HTTPS with a pin first. The REST SPKI pin is kept only after a call carrying the PSK (or the code, or its cookie) gets a 2xx. Certificate renewal with the same key is transparent; a changed key fails closed and asks for pairing again. A successful Remote v2 pairing may refresh REST trust by probing without PSK/cookie and storing the observed HTTPS public key before normal IP control restarts. If that probe fails, the old pin stays; it is never silently replaced. HTTP is used only for a TV never pinned, only once unauthenticated discovery answered over HTTP, and only to private addresses (`LanAddress`). The PSK never goes on discovery or on an icon over HTTP. On an HTTP-only TV it does travel in clear on the LAN, which is inherent to that TV. |
| A LAN host impersonates the TV's Cast receiver to feed false "now playing" | Device authentication against Google's bundled Cast roots, with the signature bound to this handshake's TLS certificate (§ 7). Until it passes, nothing is read, and nothing but the challenge is sent. Nothing secret ever goes over this channel: it is read-only and has no client certificate. Titles are redacted in `toString` and never logged. |
| A Cast status points the phone at an arbitrary URL (tracking pixel, LAN probe, oversized image) | The status is read only after device auth (§ 7); even then only HTTPS on port 443 to `i.ytimg.com` or `lh3.googleusercontent.com` is fetched (`CastArtwork`, tested), with no redirects, cookies or credentials, at most 512 KiB and 4096 px a side. A private address or any other host is never asked. |
| The soundbar port has no authentication | Inherent to the device: anyone on the LAN can already control it. The app adds nothing exploitable and exposes no listening port. |
| Secrets leak through backups, logs or crash reports | Encrypted with an AndroidKeyStore key, stored in two paths excluded from cloud backup and device transfer; `Redact` and header-free logging; `SessionKeys.toString` is redacted. |
| Client key extraction from a stolen phone | The TLS key is generated non-exportable in AndroidKeyStore where the TLS stack allows; otherwise (fallback) encrypted at rest. Device lock protects the rest. |
| Sony account compromise via the app | Sign-in is opt-in, OAuth PKCE in a Custom Tab (the app never sees the password, no WebView), tokens scoped to device control and wiped by "Se déconnecter de Sony". |
| Malicious or malformed device traffic | Every decoder is total: bad lines and frames become `Malformed` or close the connection; frame size is bounded (1 MiB), line length bounded (64 KiB). |
| A tampered APK update | Releases are signed with one long-lived key held only in GitHub secrets; Android refuses updates signed otherwise. A final release fails without that key: it never publishes an unsigned APK, nor one signed with `app/debug.keystore`. Until the key exists, a `-dev` tag still ships the debug build as a pre-release (Erwann, 2026-10-25). That debug key is public (committed, password `android`), so anyone can sign an "update" over such a build: install those on test phones only. |
| A tampered update through the in-app updater | It adds no new trust: it only fetches `kud/tutti`'s own releases, over verified HTTPS to GitHub's hosts, checks the reported SHA-256 and the package, and Android checks the signature and asks to confirm. The digest proves the file is the one GitHub published, not who published it: whoever can publish a release on `kud/tutti` can ship an update, exactly as before the updater. While dev builds carry the public debug key, that includes anyone who can get Erwann to sideload an APK by hand; the updater never does. |
| A HID keyboard can do anything a person at the TV can | The role is held only while the Bluetooth screen is in front, and only the TV that paired through Android's own dialog (code shown on both) can connect. Every report comes from a touch, a key or the gyroscope on that screen, never from the network. No secret is stored: the remembered TV is a Bluetooth address in plain prefs. The 120 s of discoverability is asked through Android's dialog, never silently. |

Out of scope: a compromised phone OS, a compromised router, physical access to the TV.
